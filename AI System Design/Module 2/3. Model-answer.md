## Scenario A — HealthBridge: Clinical Knowledge System

### Section 1 — Document Ingestion and Chunking Strategy

**Chunking strategy and rationale:**

HealthBridge's corpus is not one corpus — it's four, with different structural properties, and they get different ingestion treatment rather than one chunking policy applied uniformly.

- **Clinical protocols (~2,400 docs) and licensed reference content (~50,000 articles):** hierarchical section-aware chunking. These documents have explicit heading structure (indication, dosing, contraindications, monitoring), and splitting along section boundaries — not character counts — preserves the unit of meaning a clinician is actually searching for. A naive fixed-size split would routinely cut a contraindication list in half, which in a clinical context is a materially worse failure than an imprecise product-search result.
- **Peer-reviewed literature (~3,000 papers):** semantic chunking within sections (abstract, methods, results, discussion treated as separate semantic units), because papers mix narrative prose with data tables and the section is the natural retrieval unit for a clinician looking for "what did this trial find," not "what does this document as a whole say."
- **Drug formulary (~8,000 entries):** *not* chunked as prose at all. Formulary entries are structured records — drug name, dosage forms, contraindications, interaction flags — and flattening them into a text chunk destroys exactly the field relationships that make the entry useful (this is the same failure mode the course covers for tabular data generally: embedding a flattened row loses the row/column relationship). Formulary entries are indexed as structured records with a parallel embedding of the free-text fields (indication summary, interaction notes) for semantic matching, and the structured fields (dose, route, interaction class) are queried directly rather than retrieved by similarity. Section 4 covers how formulary questions get routed differently from protocol questions.
- **Contextual chunk enrichment on all prose chunks:** clinical writing is dense with unresolved references — "the medication," "the target population," "the recommended dose" — that only resolve against the document's subject entity. Every chunk gets the document title, the primary drug/condition entity, and the document's effective date injected before embedding. Without this, a chunk reading "contraindicated in patients with the condition" loses which condition the moment it's separated from paragraph one.

**Chunk size:** 400 tokens (prose) **Overlap:** 60 tokens **Minimum chunk size:** 120 tokens (formulary entries are indexed as complete structured records regardless of token count)

**Metadata schema:**

| Field | Type | Purpose |
|---|---|---|
| `document_type` | enum (protocol / formulary / reference / literature) | Routes queries to the correct retrieval path and lets pre-filters exclude irrelevant content types |
| `effective_date` / `version_id` | date / string | Staleness detection — flags whether a chunk is from the current or a superseded protocol version |
| `subject_entities` | array[string] | Injected drug/condition entities for the coreference-enrichment step and for entity-scoped pre-filters |
| `source_system` | string | Traceability back to the licensing agreement or internal authoring system, needed for the citation shown to the clinician |
| `clinical_specialty_tags` | array[string] | Lets a query from an oncology pharmacist deprioritize cardiology-tagged content when ambiguous |

### Section 2 — Embedding Model Selection

**Model: BGE-large (open-weight, self-hosted), 1024 dimensions.**

The controlling constraint here isn't quality, it's HIPAA: all data must stay on HealthBridge infrastructure, and clinician queries frequently carry patient context even though the corpus itself is reference material. Sending query text to a third-party embedding API means sending that patient context off HealthBridge's infrastructure on every single query — not an occasional exception, the normal operating mode. That rules out API-based embedding (OpenAI text-embedding-3, Cohere) regardless of their quality, and makes self-hosted open-weight the only compliant option. BGE-large is deployed inside HealthBridge's own infrastructure so no query or document text ever leaves it.

Query and document chunks are embedded by the same model instance — this is a hard requirement, not a preference, because the similarity calculation between a query vector and a chunk vector is only meaningful if both were produced by the same embedding space.

**What would trigger a full re-embedding:** (1) upgrading to a newer BGE or comparable model version for a material quality gain — this is a full-corpus migration, not a config change, so it's evaluated deliberately, not adopted the week a new model ships; (2) a governance decision that a different model family is required (e.g., a clinically-tuned embedding model becomes available and passes HealthBridge's validation process); (3) discovering — via the retrieval-quality monitoring described in Section 5 — that a systematic class of clinical queries is underperforming in a way traced to embedding quality rather than chunking or retrieval configuration.

---

### Section 3 — Vector Store Selection

**Selected vector store: Qdrant, self-hosted on HealthBridge infrastructure.**

**Tradeoffs considered:**

The compliance constraint is addressed first, not last: HIPAA plus the on-premise requirement rules out any managed vector database whose infrastructure HealthBridge doesn't control, which eliminates Pinecone outright regardless of its operational advantages. That leaves self-hosted options: Qdrant or pgvector.

pgvector was seriously considered — HealthBridge doesn't currently run a Postgres deployment at the scale this system needs, and pgvector's hybrid search requires running a separate full-text query and merging results in application code rather than getting native fusion. Given that hybrid search (semantic + keyword, needed for exact drug-name and code lookups — Section 4) is a day-one requirement here, not a later addition, Qdrant's native hybrid search with sparse vector support removes engineering surface HealthBridge would otherwise own and maintain. Qdrant also has stronger native metadata filtering, which matters for the specialty and document-type pre-filters in Section 4.

**Why alternatives were ruled out:** Pinecone — data residency violation, not a capability gap. Chroma — explicitly a prototyping tool per the vector database tooling lesson, not appropriate for a production system serving 8 hospitals and 40 clinics. pgvector — viable and compliant, but loses on hybrid search ergonomics and metadata filtering depth for a corpus this heterogeneous; it remains the fallback if Qdrant's operational overhead proves too high for the team's current capacity.

**Index type: HNSW.** At roughly 63,400 source items (well under the ~50M-vector threshold where HNSW's memory profile becomes the binding constraint), and given that a missed retrieval in a clinical Q&A context is a user-visible, safety-relevant failure — exactly the case where the course's default guidance ("recall matters, HNSW wins") applies without qualification.

### Section 4 — Retrieval Design

**Query strategy:** Hybrid search (semantic + BM25), fused with reciprocal rank fusion. Semantic search alone would regularly miss exact drug names, NDC codes, and dosage figures — precisely the identifiers BM25 catches and vector similarity does not.

Before retrieval, a query classifier routes the request: structured formulary questions (dosing, interaction lookups against a specific drug pair) go to a direct structured query against the formulary's indexed fields, not vector retrieval — the same text-to-structured-query pattern the course describes for tabular data, applied here to the formulary records specifically. General clinical questions (protocol lookups, "what does the guideline say about X") go through the standard hybrid RAG path. Questions that plausibly touch both (a drug's interaction profile *and* the protocol context for using it) are merged: both paths run, and results are combined before generation.

**Query transformation:** Query rewriting is required before embedding — this is a conversational interface (clinicians ask follow-up questions), and a bare follow-up like "what about renal impairment?" means nothing on its own without the prior turn's drug context. For compound clinical questions ("dosing for metformin in a diabetic patient with stage 3 CKD"), query decomposition splits the question into its constituent lookups (base dosing + renal adjustment factor) so each sub-question retrieves against its own best-matching content rather than one query trying to match both.

**Reranking decision:** Applied. A cross-encoder reranker (BGE Reranker, self-hosted for the same residency reason as the embedding model) reorders the top candidates before generation. The added 100–300ms latency is acceptable here — this is not a sub-second interactive product-search experience, it's a clinical lookup tool where correctness dominates the latency budget.

**Chunks retrieved → passed to model:** 25 initial → 5 final (after reranking).

**Metadata pre-filters:** `document_type` (exclude formulary records from a protocol-only query and vice versa, unless the merged path applies), `version_id` (exclude superseded protocol versions — current-only unless the clinician explicitly asks for historical guidance), `clinical_specialty_tags` (soft boost, not a hard exclude, since cross-specialty relevance is common in medicine).

**Retrieval quality gate (absence blindness mitigation):** Before generation, retrieval confidence is scored against a calibrated threshold. Below threshold, the system does not call the generation model at all — it returns "no relevant guidance found in the indexed corpus for this question" and offers escalation to a clinical resource librarian. This is a hard architectural gate, not a prompt instruction, because a model cannot reliably distinguish "I found the right answer" from "I found the closest thing available" — the two look identical from the inside.

### Section 5 — Evaluation Plan

| RAGAS Metric | Target Threshold | Breach Response |
|---|---|---|
| Faithfulness | ≥ 0.97 | Investigate whether the generation prompt's grounding instruction is being followed and whether the model is supplementing retrieved context with training-memory knowledge about drugs/conditions — a near-zero-tolerance metric given the clinical stakes of a fabricated claim |
| Context Precision | ≥ 0.85 | Investigate chunking and reranking — low precision usually means the reranker isn't demoting near-miss chunks (e.g., a different drug in the same class) |
| Context Recall | ≥ 0.90 | Investigate coverage gaps in the corpus or embedding quality — this is the metric most likely to catch a formulary update that wasn't re-ingested |
| Answer Relevancy | ≥ 0.88 | Investigate query rewriting — a drop here on multi-turn conversations usually traces back to the follow-up question not being condensed against prior turns before embedding |

**Non-automated evaluation:** A standing panel of two clinical pharmacists reviews a monthly sample of flagged and randomly-selected interactions against a golden query set of ~150 hand-curated questions with known-correct answers and source documents, built jointly with the pharmacy team. This is the mechanism that catches the gap RAGAS structurally can't see: a response can be perfectly faithful to what was retrieved while the retrieved content is simply the wrong answer because the real answer was never indexed. The golden set doubles as the recall@k measurement basis referenced in the course's evaluation-data lesson.

## Scenario B — LexAI: Legal Research Assistant

### Section 1 — Document Ingestion and Chunking Strategy

**Chunking strategy and rationale:**

Meridian & Partners' corpus is exactly the entity-heavy, referentially dense case the course flags as the decision point for proposition-based chunking. Legal writing is saturated with unresolved references — "the plaintiff," "the acquiring entity," "the respondent in the original proceedings" — and a query for "cases where Acme Corp prevailed" will not match a chunk that only ever says "the plaintiff prevailed," because the embedding never contains "Acme Corp."

Rather than paragraph- or section-based chunking with enrichment as the primary strategy (adequate for the HR-style corpus in Scenario A/the case studies), LexAI's corpus justifies the more expensive proposition-based approach: each chunk is a self-contained, attributable claim with every entity resolved at index time — "Acme Corp filed for regulatory approval on 2024-03-15" rather than "the acquirer then filed." This costs an LLM pass over every document at index time (materially more expensive and slower than naive or section-based chunking) but the corpus characteristics justify it: entity-heavy content, and research questions ("what's our precedent for X") that are fundamentally about specific parties, holdings, and relationships, not about a document's general topic.

Contextual enrichment (document title, matter ID, filing date, court) is applied on top of the proposition extraction, since even a resolved proposition benefits from knowing which matter and which court it came from.

**Chunk size:** 250 tokens (propositions are naturally shorter than paragraph-based chunks) **Overlap:** 20 tokens (minimal — propositions are self-contained by design, so overlap is a smaller safety margin than in prose chunking) **Minimum chunk size:** 80 tokens

**Metadata schema:**

| Field | Type | Purpose |
|---|---|---|
| `matter_id` | string | **Access control, not just organization** — the field that enforces attorney-client privilege boundaries at the retrieval layer (Section 4) |
| `document_type` | enum (brief / memo / correspondence / transcript / external case law) | Distinguishes internal work product from Westlaw-sourced external precedent for citation and trust-tier purposes |
| `resolved_entities` | array[string] | The entities resolved during proposition extraction — parties, courts, case numbers — used both for retrieval and as the seed data for the knowledge graph described in Section 4 |
| `filing_date` / `court` | date / string | Supports recency and jurisdiction-scoped queries |
| `content_provenance` | enum (internal / external-adversarial / external-neutral) | Trust-tier tagging — a filing from opposing counsel is untrusted content to reason over, not an instruction source, and needs to be labeled as such before it reaches the model's context |

---

### Section 2 — Embedding Model Selection

**Model: E5-large (open-weight, self-hosted), 1024 dimensions.**

Attorney-client privilege is the controlling constraint, and it's stricter than a residency requirement — the corpus contains confidential client-matter information that must never leave firm-controlled infrastructure, full stop. That rules out any API-based embedding provider (OpenAI, Cohere) regardless of quality, since every embedding call would otherwise transmit case content to a third party. Self-hosted, open-weight is the only architecture that satisfies the constraint, mirroring HealthBridge's reasoning in Scenario A but with a harder line — there's no "reference material without patient identifiers" carve-out here; case files themselves are the privileged content.

The query embedding and chunk embeddings are produced by the same firm-hosted model instance for the reasons already covered — coupled embedding spaces are non-negotiable for meaningful similarity search.

**What would trigger a full re-embedding:** a firm-wide model upgrade decision (evaluated and approved, given the migration cost); a demonstrated retrieval-quality gap on multi-hop or entity-specific queries traced to embedding rather than chunking; or a change in proposition-extraction methodology that changes what's being embedded (e.g., moving from proposition-only to proposition-plus-context chunks), which effectively requires treating the corpus as re-ingested from scratch.

---

### Section 3 — Vector Store Selection

**Selected vector store: Qdrant, self-hosted on firm-controlled infrastructure.**

*Note: this scenario's query pattern also requires a knowledge graph as a second retrieval component alongside the vector store — see Sections 4 and 6. This section addresses the vector store specifically, per the worksheet's scope.*

**Tradeoffs considered:**

As with HealthBridge, the compliance constraint narrows the field first: data must never leave the firm's controlled infrastructure, which eliminates Pinecone regardless of its operational advantages. Between the remaining self-hosted options, pgvector was considered and set aside for the same reason as Scenario A — hybrid search would require a hand-built fusion layer rather than native support, and at ~2 million case documents plus a curated external case-law library, the corpus is large enough that Qdrant's native hybrid search and stronger metadata filtering (critical here — see below) earn their added operational overhead over pgvector's simplicity.

The metadata filtering requirement is not a nice-to-have in this scenario — it is the mechanism that prevents one client's confidential information from surfacing to an attorney working a different matter. That filter must be a pre-filter applied at the index level, not a post-processing step run after similarity search against the full corpus; running the vector search across confidential material the requesting attorney isn't authorized to see and only removing it afterward means the similarity computation itself touched privileged content it shouldn't have. Qdrant's strong native metadata filtering support was weighted heavily for this reason.

**Why alternatives were ruled out:** Pinecone — data-residency/privilege violation. Chroma — prototyping tool, not appropriate at this scale or for this trust boundary. pgvector — compliant and viable, but the hybrid-search retrofit cost and comparatively weaker filtering depth make it the fallback rather than the primary choice.

**Index type: HNSW**, for the same reasoning as HealthBridge — corpus size (~2M documents plus external case law, still well under HNSW's practical ceiling) and a domain where a missed precedent is a high-consequence, user-visible failure, not a tolerable approximation.

---

### Section 4 — Retrieval Design

**Query strategy:** Hybrid at the vector-retrieval layer, *plus* a structurally separate graph-traversal path — this scenario is where standard RAG genuinely isn't sufficient on its own. A meaningful share of associates' real research questions are entity-relational: "find cases where Company X was the defendant and the ruling involved IP infringement, with a cross-border jurisdiction element." That is not a similarity question; it's a traversal question, and no amount of reranking or query rewriting turns vector search into graph traversal.

The architecture therefore includes a knowledge graph (Neo4j) built at index time from the same proposition-extraction pass described in Section 1: entities (companies, individuals, courts, jurisdictions) as nodes, relationships ("defendant in," "appealed to," "cited as precedent in") as edges. A query classifier — the same routing pattern the course describes for structured-vs-semantic queries — determines whether an incoming question goes to vector retrieval, graph traversal, or both merged before generation. Simple "what's our precedent for X" questions typically resolve well via hybrid vector search. Multi-part relational questions route to graph traversal. Compound questions merge both.

**Query transformation:** Query decomposition for multi-part relational questions before they even reach the classifier — breaking "Company X, defendant, IP infringement, cross-border" into its constituent filters makes the downstream graph traversal tractable and makes it possible to tell a genuine multi-hop question from a question that merely sounds complex but is answerable by a single vector lookup.

**Reranking decision:** Applied on the vector-retrieval path (cross-encoder, top candidates reordered before generation) — reranking on the graph-traversal path is not applicable in the same sense, since traversal results are deterministic given the graph, but the *documents* attached to matching graph nodes still go through relevance reranking before being assembled into context.

**Chunks retrieved → passed to model:** 30 initial → 8 final (vector path); graph traversal returns matching case nodes directly rather than a top-k similarity list, with associated source documents capped at 8 per case node for context budget reasons.

**Metadata pre-filters:** `matter_id` is the load-bearing filter here — every retrieval, vector or graph, is scoped to the matters the requesting attorney is authorized to see, applied as a pre-filter before search executes, not after. `content_provenance` is used to tag retrieved content from opposing-party filings as untrusted-to-reason-over rather than instruction-bearing, given that formal legal drafting is exactly the kind of text that could smuggle an instruction-shaped sentence past a model that trusts retrieved content by default.

**Absence handling — the honest version:** "No matching nodes" in the graph doesn't mean "no such precedent exists" — it means nothing matching was captured by the extraction pipeline, and extraction can miss entities or drop relationships. Absence is explicit relative to extraction recall, which is testable and improvable, not relative to ground truth in the raw corpus. This is communicated to the associate in the response itself ("no matching precedent found in the indexed corpus" rather than an unqualified "no such precedent exists"), and extraction recall is sampled and monitored as an ongoing metric, not a one-time validation.

### Section 5 — Evaluation Plan

| RAGAS Metric | Target Threshold | Breach Response |
|---|---|---|
| Faithfulness | ≥ 0.95 | Investigate whether generated summaries are citing case content that isn't actually in the retrieved documents — a faithfulness breach here is a malpractice-exposure risk, not just a quality metric |
| Context Recall | ≥ 0.90 | Investigate corpus coverage and graph extraction recall — the metric most likely to catch a precedent that exists but wasn't captured by entity extraction |
| Context Precision | ≥ 0.80 | Investigate coreference resolution quality and reranking — set slightly lower than HealthBridge's because entity-heavy legal prose is inherently noisier for a reranker to score cleanly, even with proposition-based chunking |
| Answer Relevancy | ≥ 0.85 | Investigate query decomposition — a drop here usually means a compound relational question wasn't broken into the right sub-questions before retrieval |

**Non-automated evaluation:** A quarterly review by two senior litigation attorneys against a golden set of ~100 known-precedent research questions, each with a verified correct answer and source case. Separately — and specific to this scenario's confidentiality requirement — a dedicated privilege-boundary red-team exercise: attorneys deliberately attempt to retrieve information from matters they are not assigned to, and any successful cross-matter retrieval is treated as a severity-one incident, reviewed by the firm's general counsel, independent of the standard evaluation cadence. RAGAS scores measure answer quality; they say nothing about whether the access-control boundary held, so that has to be tested directly.

## Scenario C — RetailMind: Conversational Product Search

### Section 1 — Document Ingestion and Chunking Strategy

**Chunking strategy and rationale:**

RetailMind's corpus doesn't have the "long document, ambiguous chunk boundary" problem the other two scenarios face — a product record (title, description, attributes, review snippets) is short relative to a clinical protocol or a legal brief. The chunking decision here is closer to a "how much do we combine" question than a "where do we cut" question.

**Strategy: record-level chunking, one primary chunk per SKU**, combining title, description, and key structured attributes (category, age range, color, price tier) into a single embedded unit, with the review corpus handled separately: the top 5 most-helpful reviews per SKU are summarized into a short "customer sentiment" field at ingestion time (via a lightweight LLM pass) rather than embedding every individual review as its own chunk — at 8 million SKUs, embedding every review independently would multiply the index size by an order of magnitude for retrieval value that a distilled sentiment summary captures at far lower cost. This is a deliberate simplification, not an oversight — full review-text semantic search is a lower-priority capability than fast, accurate product matching against a conversational query.

Fixed-size chunking is explicitly the wrong default here (per the course's naive-chunking anti-pattern) — but the reason it's wrong for RetailMind isn't the usual "cuts mid-sentence" failure, it's that a fixed character count has no relationship to a product record's natural boundary, which is the SKU itself.

**Chunk size:** ~150 tokens (title + description + attribute summary; most product records fit comfortably) **Overlap:** 0 (record-level chunking — there is no adjacent-chunk context to preserve within a single product's boundary) **Minimum chunk size:** 40 tokens (thin records — e.g., commodity items with minimal description — are still indexed rather than dropped)

**Metadata schema:**

| Field | Type | Purpose |
|---|---|---|
| `sku_id` | string | Primary key; joins back to live inventory/pricing systems for real-time price and stock accuracy |
| `category` / `attribute_tags` | string / array[string] (price, age-range, color, material, etc.) | The pre-filters that do the heavy lifting in this scenario — see Section 4 |
| `last_updated` | timestamp | Freshness tracking — the catalog changes continuously, and stale product data (discontinued items, price changes) is a direct customer-trust problem |
| `in_stock` | boolean | Hard filter — an out-of-stock item should not consume a slot in a latency-constrained top-k result |
| `review_sentiment_summary` | string | Distilled review signal (see above), embedded as part of the record rather than as separate chunks |

---

### Section 2 — Embedding Model Selection

**Model: BGE-small (open-weight, self-hosted), 384 dimensions.**

No compliance constraint forces self-hosting here — this is consumer product data, not regulated health or privileged legal content — but two other factors point the same direction as the compliance-driven scenarios: cost and latency. At 8 million SKUs with continuous catalog updates, an API-based embedding provider means a per-call cost that compounds every time inventory changes, and — more importantly given the hard 300ms P95 constraint on the parsing layer — a network round-trip to an external API on the query path is latency RetailMind can't spend. A smaller, self-hosted, colocated model (384 dimensions vs. 1024+ for the larger models used in Scenarios A/B) trades a small amount of embedding quality for materially lower query-time latency and full control over the inference path — the right tradeoff when the corpus is short product records rather than dense clinical or legal prose where nuance matters more.

**What would trigger a full re-embedding:** a catalog-wide attribute schema change (e.g., adding a new structured attribute category that changes what's in the embedded text); a measured retrieval-quality regression on conversational queries traced to embedding rather than the query-parsing layer; or a decision to upgrade to a larger embedding model if evaluation shows the current model is the binding constraint on relevance — evaluated against the latency cost of a larger model before adopting it, not adopted automatically for a quality bump.

---

### Section 3 — Vector Store Selection

**Selected vector store: Qdrant, self-hosted, colocated with the existing Elasticsearch infrastructure.**

**Tradeoffs considered:**

There's no compliance requirement to address first in this scenario, which makes it tempting to default straight to "whichever is fastest" — but the actual first-order constraint is the 300ms P95 latency budget on the parsing layer, and that reframes the vector-store decision as a latency and integration question rather than a pure performance benchmark. A managed option like Pinecone would add a network hop to a third-party service on every query; at RetailMind's query volume (15 million registered users) that's both a latency risk against the hard budget and a meaningful per-query cost. Self-hosting Qdrant colocated with the existing Elasticsearch cluster keeps the retrieval path in-network.

pgvector was considered given RetailMind likely already runs relational infrastructure for inventory and pricing, but was ruled out on two grounds: expected query volume and throughput at this catalog scale exceed what the course flags as pgvector's comfort zone, and native hybrid search matters as much here as in the other two scenarios — a shopper's query for an exact brand name or model number needs BM25-style exact matching alongside the semantic "gift for a 7-year-old who likes dinosaurs" style query, and Qdrant provides that natively rather than requiring a hand-merged second query.

**Why alternatives were ruled out:** Pinecone — network-hop latency risk against a hard 300ms budget, plus cost at this query volume. Chroma — not a production-scale option. pgvector — viable in principle but a weaker fit for the throughput and native hybrid-search requirements at 8M SKUs with continuous writes.

**Index type: HNSW**, with **scalar quantization** applied given the corpus scale — 8 million 384-dimension vectors is well within HNSW's practical ceiling (the course puts that around 100M), but quantization is used to keep the in-memory footprint manageable and query latency predictable at RetailMind's query volume, accepting the small recall cost quantization introduces since it's recoverable via the pre-filter and fusion design in Section 4. Catalog churn (continuous SKU updates) is handled as incremental index updates, not full rebuilds — full re-indexing is only triggered by an embedding-model change, not by ordinary catalog churn, so IVF's faster full-rebuild cycle isn't the deciding factor here the way it might be for a corpus with frequent embedding-model turnover.

---

### Section 4 — Retrieval Design

**Query strategy:** Hybrid search (semantic + BM25), fused via reciprocal rank fusion — semantic search handles "birthday gift for a 7-year-old who likes dinosaurs," BM25 catches exact brand names, model numbers, and SKU-adjacent identifiers that semantic similarity would miss entirely.

Structured attributes (price ceiling, category, age-appropriateness) are **not** left to the semantic layer to infer approximately — they're extracted by the query-parsing layer as explicit filter values ("under $40" → `price <= 40`) and applied as hard pre-filters at the vector-store query level, the same pre-filter-not-post-filter principle used for access control in Scenarios A and B, applied here for correctness and latency rather than security: filtering before search means the similarity computation only runs over the already-narrowed candidate set, which is faster, not just more correct.

**Query transformation:** Conversational query rewriting is essential and non-negotiable here — the scenario's own example ("make it blue" as a follow-up) is precisely the case the course flags as breaking any system that embeds the literal last message. "Make it blue" carries no product context on its own; it has to be condensed against the prior turn ("birthday gift for a 7-year-old who likes dinosaurs under $40, in blue") before embedding.

**Reranking decision: not applied as a full cross-encoder pass on the primary path**, and this is a deliberate, latency-driven exception to the course's general reranking guidance, not an oversight. A cross-encoder rerank typically costs 100–300ms on its own — spending that against a 300ms P95 *total* budget for the parsing layer isn't viable. Instead: the RRF-fused hybrid score is used directly for the top-k ordering, and a much lighter-weight learned reranking step (a small, fast model scoring the already-filtered top-20 candidates, budgeted at under 20ms) is applied where the time budget allows. This tradeoff is monitored explicitly — if evaluation shows the fused score alone is producing a meaningfully worse-ordered result set than a full rerank would, that's a signal to revisit the latency budget allocation (e.g., trimming the query-parsing step further) rather than silently accepting degraded ranking quality.

**Chunks retrieved → passed to model:** 100 initial → 20 final (this scenario surfaces a ranked product set for a UI grid/carousel, not a single generated prose answer, so "passed to model" here means passed to the response-composition layer that formats the product set and any accompanying conversational text).

**Metadata pre-filters:** `category`, `price` (range), `attribute_tags` (age-range, color, material), `in_stock` — applied before the hybrid search executes, both for correctness (a shopper asking for "under $40" should never see a $60 item) and for the latency benefit of narrowing the candidate set before the more expensive similarity computation runs.

### Section 5 — Evaluation Plan

| RAGAS Metric | Target Threshold | Breach Response |
|---|---|---|
| Context Precision | ≥ 0.75 | Investigate the attribute-extraction step in query parsing — a precision drop usually means extracted filters (price, category) are too loose or the semantic match is surfacing off-topic products |
| Context Recall | ≥ 0.80 | Investigate catalog coverage and embedding quality for underrepresented categories — set below the health/legal thresholds because exploratory retail search tolerates more near-miss variation than a clinical or legal lookup does |
| Answer Relevancy | ≥ 0.85 | Investigate query rewriting — a drop on multi-turn sessions (the "make it blue" pattern) points directly at the conversational condensing step |
| Faithfulness | ≥ 0.93 | Investigate whether generated product descriptions or comparison text include specifications not present in the actual product record — lower stakes than clinical/legal fabrication, but a direct driver of return-rate and customer trust |

**Non-automated evaluation:** Continuous human relevance labeling on a sampled stream of live conversational queries (in-house catalog/merchandising team judges whether the top-20 results match query intent), supplemented — not replaced — by online behavioral signals: click-through and add-to-cart rate on returned results, tracked as a correlational quality proxy and explicitly flagged as such, since a high click-through rate reflects what's visually appealing in a result grid as much as what's actually relevant to the stated query. RetailMind's scale makes behavioral data unusually cheap to collect relative to HealthBridge or LexAI, and it supplements the hand-labeled judgments rather than substituting for them.

## Rubric Commentary

**Chunking strategy specificity.** The three scenarios should produce visibly different chunking decisions, and that's the point — a good answer's chunking choice is derived from the corpus's actual structure (long referential prose vs. short structured records) and the query pattern (single-document lookup vs. entity-relational vs. attribute-filtered product matching), not copy-pasted from a "best practice" list. A common mistake is picking one chunking strategy (usually "semantic chunking, 500 tokens, 50 overlap") and applying it identically regardless of scenario — that's a tell that the strategy wasn't actually derived from the corpus. Notice that HealthBridge and LexAI both have entity-reference problems but land on different remedies (contextual enrichment vs. full proposition-based chunking) because LexAI's queries are more purely entity-relational — a good answer explains *why* the more expensive strategy is or isn't justified, not just names it.

**Embedding model choice.** All three scenarios in this model answer land on self-hosted, open-weight models, but for different reasons — HIPAA and privilege force it in A and B; cost and latency justify it in C, where there's no compliance requirement blocking API use. A common mistake is naming "OpenAI text-embedding-3" as the default answer without checking whether the scenario's compliance constraint rules it out entirely (HealthBridge and LexAI both would forbid it), or naming a self-hosted model in Scenario C without justifying why, given that nothing forces the choice — the rubric wants the reasoning shown, not just a defensible-sounding model name.

**Vector store selection.** The rubric explicitly wants compliance addressed *before* capability tradeoffs, and the difference between scenarios shows why that ordering matters: in HealthBridge and LexAI, Pinecone is eliminated in one sentence by the residency/privilege constraint, no benchmark required. In RetailMind, there's no such constraint, so the same conclusion (self-hosted Qdrant) has to be earned through an actual latency and cost argument. A common mistake is treating "data must stay on-premise" as a footnote after a features comparison, when it should be the first filter applied — most of the candidate field is eliminated before capability tradeoffs are even relevant. A second common mistake, specific to LexAI: naming only a vector store when the scenario's query pattern (explicit multi-hop entity questions in the prompt) is a strong signal that a graph component is also required — an answer that stops at "Qdrant, done" hasn't actually solved the stated problem.

**Retrieval design completeness.** All four elements — query strategy, transformation, reranking, chunk counts — need explicit values, and "we'll figure out reranking during implementation" is exactly the open decision the rubric is checking hasn't been left dangling. RetailMind's reranking decision is the most instructive case across the three: the *correct* answer is not "always rerank" (the course's general guidance) but a justified, monitored exception to it, because the 300ms hard latency budget makes a full cross-encoder pass structurally incompatible with the requirement. A common mistake is either applying the general rule mechanically without checking it against the scenario's stated constraint, or dropping reranking silently without acknowledging the tradeoff being made. Good answers show the reasoning for *why* the general pattern doesn't apply here, and what compensates for the gap.

**RAGAS metric selection.** Thresholds need to be numbers, and the numbers need to differ by scenario in a way that reflects the actual stakes — a faithfulness breach in HealthBridge (a fabricated clinical claim) is categorically more dangerous than one in RetailMind (an inaccurate product description), and the thresholds in this model answer reflect that gradient (0.97 vs. 0.93) rather than using one blanket number everywhere. A common mistake is listing the four RAGAS metrics with a generic target like "high score" or ">90%" across the board without connecting the number to what a breach would actually mean for that specific system, and a second common mistake is forgetting the non-automated evaluation requirement entirely — every scenario here needs it precisely because RAGAS structurally cannot detect the absence-blindness gap (a response can be perfectly faithful to a retrieved chunk that was simply the wrong chunk because the right one was never indexed).

**Architecture diagram.** Both the offline ingestion and online retrieval pipelines need to appear, connected, with the components the worksheet names explicitly called out — including observability hooks, which are the component most often dropped from a first-draft diagram. LexAI's diagram is the one most likely to be built incorrectly: a common mistake is drawing a single linear RAG pipeline and bolting the knowledge graph on as an afterthought box, rather than showing the query classifier as a genuine fork with two structurally different retrieval paths that merge back before generation, which is the actual shape of the system the scenario calls for.

**Overall quality signal.** The test the worksheet poses — could a senior engineer implement this without making major design decisions themselves — is failed by any answer with an unresolved "it depends" left in a load-bearing spot: an unnamed embedding model, an unset chunk size, a reranking decision deferred to "we'll see." It's passed by an answer where every number and every tool name is either taken from the scenario's stated facts or justified against them in the same paragraph it appears in.
