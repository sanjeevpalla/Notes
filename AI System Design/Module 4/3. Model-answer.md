## Scenario A — HealthBridge: EHR Integration

**Recap of scenario facts used below:** Epic EHR (FHIR R4, read patient context / write completed notes), Azure AI Speech speech-to-text (already deployed), Epic scheduling (read-only), Azure AD auth, self-hosted note-generation model on HealthBridge infrastructure. Launch scale (from the Module 3 memo this design continues): 2,000 encounters/day, growing to 10,000/day at 18 months, across 8 hospitals and 40 clinics.

### Section 1 — Integration Layer Design

**Gateway design and rationale:**

Even though HealthBridge has exactly one AI capability today (SOAP note generation from a self-hosted model), a dedicated gateway is still justified, for reasons specific to this environment rather than generic ones:

- **Multi-site rate limiting.** The self-hosted model runs on a fixed GPU allocation. Eight hospitals and 40 clinics all generating notes at encounter end creates a shared-capacity problem identical in shape to the e-commerce case study's shared-infrastructure problem, even though there's only one model and one deployer. Without a gateway, there is no place to enforce per-site fair-share limits, and a single high-volume hospital during a flu-season surge could starve smaller clinics of inference capacity.
- **Centralized PHI-safe logging.** The requirement that "PHI must not appear in any log without redaction" is a cross-cutting concern. Implemented once at the gateway (redact transcript content and structured note fields before they hit the logging pipeline, log only encounter IDs, token counts, latency, and validation outcomes), it can't be forgotten by a future second AI feature the way it could be if every calling service redacted independently.
- **Single circuit-breaker point for the degrade-to-manual behavior.** Because "the system must degrade gracefully — encounters still happen, notes still get written manually," the fallback logic (below) needs one place to watch error rate and latency and flip the whole note-generation path off. That place is the gateway, not each calling service.
- **Future-proofing.** HealthBridge will likely add a second AI capability (e.g., coding/billing suggestion) within the 18-month scale-up window. Building the gateway now means that addition is a routing config change, not a new integration project.

Given the self-hosted, on-premise constraint, this is **not** a case for a managed cloud gateway (Bedrock/Azure AI Foundry/Vertex) — those require the request to leave HealthBridge's private cloud at the gateway layer, which conflicts with the PHI data-residency requirement. This is the textbook case the course flags for **LiteLLM Proxy, self-hosted inside HealthBridge's private cloud**, fronting the self-hosted model. It gives routing, rate limiting, cost attribution (by hospital/clinic cost center), and caching without any request ever transiting a third-party endpoint.

**Adapter interface contract:**

```
// Internal service interface — application services (the encounter workflow
// service that listens for STT completion) call this, never the gateway
// or the model directly.

interface ClinicalNoteAdapter {
  generateNote(request: NoteGenerationRequest): Promise<NoteGenerationHandle>
  getNoteResult(taskId: string): Promise<NoteDraftResult | NotReadyYet>
}

NoteGenerationRequest {
  encounter_id: string          // from Epic schedule
  transcript_ref: string        // pointer to Azure STT output, not inline PHI
  patient_context_ref: string   // pointer to FHIR context bundle, fetched separately
  requesting_site: string       // hospital/clinic ID, for rate limiting + cost attribution
}

NoteGenerationHandle {
  task_id: string
  status: "queued" | "processing"
}
```

The adapter is deliberately thin: it does not accept a raw prompt, a model name, or a provider SDK object. If HealthBridge later swaps the self-hosted model for a different one, or adds a second model for a specific note type, only the adapter's internal implementation changes — the encounter workflow service that calls `generateNote()` never changes.

**Request/response pattern for each AI feature, with justification:**

There is one AI feature — SOAP note generation — with two distinct interaction paths:

| Interaction | Pattern | Justification |
|---|---|---|
| Note generation at encounter end | **Asynchronous (task queue)** | A 15–45 minute transcript is a substantial input; end-to-end generation is not a sub-3-second operation, so per the module's guidance this is squarely async territory. The physician isn't sitting waiting for it — they move to the next patient. Encounter-end (a webhook from Azure STT completion) submits the task; the physician is notified (Epic in-basket / task list) when the draft is ready for review. |
| Physician-initiated "regenerate this section" during review | **Synchronous with streaming** | If a physician edits the Assessment and asks the system to regenerate the Plan section against the edited context, that's an interactive, in-session action — the physician is actively waiting. Stream tokens so time-to-first-token, not total generation time, drives perceived responsiveness. |

### Section 2 — Output Handling Strategy

**Output schema (SOAP note generation):**

```json
{
  "encounter_id": "string, required",
  "generated_at": "ISO-8601 timestamp, required",
  "model_version": "string, required",
  "note": {
    "subjective": "string, required, non-empty",
    "objective": "string, required, non-empty",
    "assessment": "string, required, non-empty",
    "plan": "string, required, non-empty"
  },
  "flags": {
    "context_incomplete": "boolean",
    "low_confidence_sections": ["string, one of: subjective|objective|assessment|plan"]
  },
  "source_transcript_ref": "string, required"
}
```

**Validation layers:**

| Layer | What it checks | Example failure |
|---|---|---|
| Schema validation | All four SOAP fields present and non-null; `encounter_id` matches a real, open encounter from Epic; `model_version` present for audit traceability | Model returns only Subjective and Objective, omitting Assessment and Plan — output rejected before it ever reaches Epic |
| Semantic validation | Note content is internally consistent with the transcript and patient context: medications named in the Plan appear somewhere in the transcript or active medication list; no vital sign in Objective that wasn't spoken in the encounter; note isn't a near-duplicate of the patient's previous visit note (a sign the model defaulted to a template instead of using this encounter) | Plan section prescribes a medication never mentioned in the 40-minute transcript — flagged as a probable hallucination, not written to Epic unreviewed |
| Business rule validation | Note length within a plausible band for encounter duration (a 45-minute encounter producing a three-sentence note is suspicious); any controlled-substance dosage in the Plan must fall within the facility's formulary range or the note is flagged for pharmacist/physician double-check; no patient identifier beyond the fields Epic's draft-note API allows in a pre-signature object | A 40-minute encounter transcript produces a 20-word note — routed to low-confidence review rather than presented as a normal draft |

**Fallback chain:**

| Failure mode | Fallback behaviour |
|---|---|
| AI unavailable | Feature flag/circuit breaker disables auto-draft generation. Physician documents the encounter exactly as before the AI system existed — nothing in the Epic workflow changes, no error is shown to the physician, and no encounter is blocked or delayed. This is the literal reading of "encounters still happen; notes still get written manually." |
| Schema validation failure | Retry once with the validation error fed back to the model ("your response was missing the Plan section — please regenerate a complete SOAP note"). If it still fails after 2 attempts, escalate: mark the draft unavailable for this encounter, notify the physician via the same in-basket mechanism used for successful drafts, physician documents manually. |
| Business rule failure after retries | Human escalation, not silent suppression: the encounter is flagged in an informatics review queue with the failed draft and the specific rule it tripped attached, so the pattern (e.g., a recurring formulary mismatch) can be diagnosed. The physician still documents manually for that encounter — a flagged draft is never surfaced as if it were a normal one. |

### Section 3 — Non-Functional Requirements

**Latency budget:**

Note generation is asynchronous and not on the critical path of the clinical encounter itself, so the relevant SLA is "draft ready before the physician next has a documentation window," not sub-second responsiveness:

- **Draft generation (async):** P50 3 minutes, P95 8 minutes from encounter-end webhook to draft-ready notification. The 45-minute-transcript case dominates the P95 — a long encounter produces a long transcript, which takes proportionally longer to process (per the module's point that token generation is sequential and scales with input/output length).
- **Interactive section regeneration (sync, streaming):** P50 2s, P95 6s, with first-token streamed within 300ms.

If the async path misses its P95, the consequence is a delayed draft, not a broken encounter — the physician simply documents that one note manually if it isn't ready by the time they'd normally chart it, and the late draft is discarded (not surfaced after the fact, to avoid a physician re-doing work). If the sync regeneration path misses its budget, the physician sees a normal "still working" streaming indicator; there is no hard timeout failure mode because they're already mid-edit, not blocked on the whole encounter.

**Caching approach:**

- **KV/prefix caching (self-hosted inference server, e.g., vLLM prefix caching):** the static system prompt — SOAP formatting instructions, HealthBridge's documentation style guide, redaction rules — is placed at the start of every prompt, with the patient-specific transcript and context appended after. This is the highest-leverage caching lever here because it applies to every single note generated, unlike exact-match or semantic caching.
- **Exact-match and semantic caching: deliberately not used** for the note content itself. Every transcript is unique PHI tied to a specific patient encounter; there is no repeated-input pattern to exploit, and caching patient-specific content — even keyed by hash — adds a PHI-retention surface with no benefit. (Contrast this with Scenario C, where query caching is the single highest-leverage optimization — the cache calculus is scenario-dependent, not a checklist to apply uniformly.)

**Graceful degradation design:**

- Feature flag per site (hospital/clinic) so a specific location can be pulled out of the auto-draft pipeline independently — useful if a data quality issue is isolated to one site's STT audio setup.
- Circuit breaker at the gateway: if the self-hosted model's error rate or P95 latency crosses a threshold (e.g., GPU cluster under unplanned load), the gateway stops accepting new generation tasks and the encounter workflow service falls straight to "no draft" rather than queuing tasks that will time out.
- The FHIR write to Epic only ever happens as a direct consequence of the physician's own approval action inside Epic — so there is no failure mode where a stale, low-confidence, or unreviewed AI output silently reaches the medical record. The write path has no AI dependency at the moment of writing.

### Section 4 — Data Pipeline

**Pipeline stages (source → processing → AI layer):**

This scenario is not a RAG knowledge-base pipeline — there's no corpus being chunked and embedded for retrieval. It's a live-context-assembly pipeline feeding a generation task, and the same "treat it as data engineering" discipline still applies:

1. **Source connector:** Azure AI Speech STT delivers a transcript via completion webhook (event-driven, not polled) — this is the trigger for the whole pipeline.
2. **Context retrieval:** at the same trigger, pull the patient's current problem list, active medications, and allergies from Epic via FHIR R4 (`Condition`, `MedicationRequest`, `AllergyIntolerance` resources), and the encounter metadata (visit type, provider, scheduled duration) from Epic, read-only.
3. **Preprocessing:** redact any PHI that shouldn't transit to the model beyond what's clinically necessary (e.g., strip patient contact/billing info that Epic's record includes but the note generator doesn't need), normalize transcript formatting (remove STT filler artifacts, tag speaker turns).
4. **Prompt assembly:** static instructions + retrieved FHIR context + transcript, in that order, for KV-cache efficiency (Section 3).
5. **Generation + validation (Section 2), delivery as a draft surfaced inside Epic** for physician review.

**Freshness SLAs:**

| Data source | Freshness SLA | How enforced |
|---|---|---|
| Patient context (Epic FHIR: problem list, meds, allergies) | Real-time — fetched live at generation time, never cached | Direct FHIR API call per generation task; no persisted copy to go stale |
| Encounter metadata (Epic schedule) | ≤ 15 minutes | Scheduled poll of Epic's scheduling interface, read-only; acceptable because this data only correlates the encounter ID and visit type, not clinical content |

**Staleness detection:**

Because patient context is fetched live rather than pre-ingested, the staleness question isn't "is our index behind the source" — it's "did the live fetch succeed and return complete data." Each generation task logs whether the FHIR context call succeeded, timed out, or returned a partial bundle. A failed or partial context fetch sets the `context_incomplete` flag in the output schema (Section 2), which routes the draft to more careful physician review rather than presenting it as a fully-grounded note. A dashboard tracks the FHIR-context-fetch failure rate; a sustained increase pages the integration on-call, since it likely indicates an Epic-side outage or an Azure AD token issue rather than a model problem.

## Scenario B — LexAI: iManage Integration

**Recap of scenario facts used below:** iManage Work 10 (DMS, REST API — case files, correspondence, memos), Aderant Expert (billing — matter numbers, client IDs, billing codes), Microsoft 365, Azure AD with matter-level access controls. Research system queries iManage; drafting system writes back to iManage as a new version. From the Module 3 memo this design continues: Meridian & Partners, 200 attorneys, IT team of 3, ~50,000 searches and ~5,000 drafting tasks per month, attorney-client privilege — client matter data cannot transit to any third-party system without explicit client consent.

### Section 1 — Integration Layer Design

**Gateway design and rationale:**

Given the firm's three-person IT team and existing Azure AD / Microsoft 365 footprint, the strongest case here is a **managed gateway — Azure AI Foundry** — rather than a self-operated LiteLLM proxy. This is a direct application of the module's managed-vs-self-hosted tradeoff: LiteLLM gives control at the cost of an operational burden the firm's IT team is not sized to carry; a managed, Azure-native gateway gives lower operational overhead and integrates with the identity system (Azure AD) the firm already runs, while still allowing model deployment within the firm's own tenant to satisfy the no-third-party-transit constraint from the privilege obligation.

Beyond the standard routing/rate-limiting/cost-attribution/caching/logging list, this scenario has one gateway responsibility that is not optional: **matter-level authorization enforcement**. The worksheet is explicit that "the integration must enforce this, not just the UI" — so the gateway (or the adapter layer immediately in front of it) must check, on every single request, that the requesting attorney's Azure AD identity has an active entitlement to the matter being queried, before the request is allowed to reach the model or the retrieval layer. This check has to live in the integration layer specifically because a UI-only restriction is trivially bypassed by anyone calling the API directly, and because both research (read) and drafting (write) sub-tasks need the identical check applied consistently.

The gateway is also the single point where every AI query and response is logged with the matter number, satisfying the billing-attribution requirement — Aderant's matter/billing-code data is the metadata tag attached to every logged request.

**Adapter interface contract:**

```
interface LegalAIAdapter {
  researchQuery(request: ResearchRequest): Promise<ResearchMemo>
  draftDocument(request: DraftRequest): Promise<DraftHandle>
  getDraftResult(taskId: string): Promise<DraftResult | NotReadyYet>
}

ResearchRequest {
  attorney_id: string       // from Azure AD
  matter_id: string         // required; checked against attorney's matter ACL
                            // BEFORE this request is constructed, not after
  query: string
}

DraftRequest {
  attorney_id: string
  matter_id: string
  document_type: string     // e.g., "NDA", "motion", "correspondence"
  context_refs: string[]    // iManage document IDs providing drafting context
}

DraftResult {
  status: "completed" | "failed"
  iManage_document_id: string   // the NEW version created, never the original
  version_note: string
}
```

The authorization check (matter ACL lookup against Azure AD group membership) is a precondition enforced by the adapter itself before any request object is even built — a request for a matter the attorney isn't entitled to never becomes a `ResearchRequest`, it's rejected at the adapter boundary with an authorization error, and that rejection is what gets logged, not a query result. This is the concrete mechanism behind "enforce this, not just the UI."

**Request/response pattern for each AI feature, with justification:**

| Feature | Pattern | Justification |
|---|---|---|
| Research query | **Synchronous with streaming** | Attorneys are interactively researching — they ask a question and wait at their desk. Streaming the memo as it's generated (rather than the full 10–20 second wait for a complete structured memo) matches the module's guidance that time-to-first-token drives perceived responsiveness for interactive use. |
| Drafting | **Asynchronous (task queue)** | Generating a full first-draft contract or motion is a multi-minute operation, well past the "2–3 seconds, async is worth it" threshold. The attorney submits the drafting request and is notified (email/M365, or an in-app notification) when the new iManage version is ready for review — they don't sit and wait for a document to be written. |

### Section 2 — Output Handling Strategy

**Output schema (for each AI feature):**

```json
// Research
{
  "matter_id": "string, required",
  "attorney_id": "string, required",
  "query": "string, required",
  "memo": {
    "issue": "string, required",
    "brief_answer": "string, required",
    "discussion": "string, required, non-empty"
  },
  "citations": [
    { "iManage_document_id": "string", "version": "string", "excerpt": "string" }
  ],
  "generated_at": "ISO-8601 timestamp"
}

// Drafting
{
  "matter_id": "string, required",
  "attorney_id": "string, required",
  "document_type": "string, required",
  "draft_iManage_document_id": "string, required",
  "based_on_version_of_original": "string",
  "sections": ["string, required, non-empty array"],
  "unresolved_placeholders": ["string"],
  "generated_at": "ISO-8601 timestamp"
}
```

**Validation layers:**

| Layer | What it checks | Example failure |
|---|---|---|
| Schema validation | Memo has non-empty `issue`/`brief_answer`/`discussion`; `citations` is an array (can be empty but must be present as a field); draft has `draft_iManage_document_id` populated and distinct from any original document ID | Drafting output omits `draft_iManage_document_id` entirely — rejected before any write to iManage is attempted |
| Semantic validation | A research memo answering a substantive case-law question with zero citations is semantically suspect for this domain and flagged even though it passes schema validation; a draft still containing template placeholders like `[INSERT PARTY NAME]` is incomplete despite being well-formed text | Memo on a precedent question returns `citations: []` — flagged as unsupported research rather than delivered as authoritative |
| Business rule validation | Every citation must reference a document the requesting attorney is authorized to access under the same matter-level ACL used at the request boundary — a memo cannot cite content from a matter the attorney isn't entitled to, even if that content was technically retrievable; `matter_id` must correspond to an active (not closed) matter in Aderant; `document_type` for drafting must be one of the firm's approved template categories | A citation resolves to a document belonging to a different, unrelated matter the attorney has no entitlement to — this is a privilege-boundary failure, not a formatting one, and is treated as a security event, not a retry candidate |

**Fallback chain:**

| Failure mode | Fallback behaviour |
|---|---|
| AI unavailable | Research: falls back to iManage's native keyword search (the pre-AI experience) — the attorney still finds documents, just without synthesis. Drafting: attorney drafts from the firm's existing Microsoft 365 templates manually. Critically, Aderant's billing/time-entry workflow is entirely unaffected either way, because it was never a runtime dependency of the AI path — it only receives attribution metadata after the fact. |
| Schema validation failure | Retry with the validation error fed back, 2 attempts. If still failing: research degrades to returning the raw retrieved documents list without a synthesized memo (a defensible degraded response — "here's what's relevant, unsummarized"); drafting fails the task and notifies the attorney to draft manually rather than delivering an incomplete document as if finished. |
| Business rule failure after retries (privilege-boundary violation) | Never retried — per the module's guidance, a business-rule failure indicates a fundamental mismatch, and in this specific case it indicates a possible cross-matter data exposure. Human escalation: block the response entirely, log a security event tagged with attorney ID and both matter IDs involved, notify the firm's information governance function. This is escalated, never silently corrected and re-served. |

### Section 3 — Non-Functional Requirements

**Latency budget:**

| Feature | P50 | P95 | Consequence of missing budget |
|---|---|---|---|
| Research query (sync, streaming) | 3s to first synthesized content | 12s to complete memo | First-token streaming keeps the attorney's perceived wait short even at P95; if the full memo exceeds ~20s, the UI shows a persistent "still researching" state rather than timing out and discarding partial work |
| Drafting (async) | 90s | 5 min (longer contracts) | No user-facing latency risk since it's async with notification — a slow draft is a delayed notification, not a broken interaction |

**Caching approach:**

- **Exact-match and semantic caching, scoped strictly per matter, never firm-wide for matter-specific facts.** Attorneys frequently ask structurally similar questions ("what's our standard indemnification language," "what's the statute of limitations for X in this jurisdiction") — a strong caching opportunity per the module's guidance on repeated-phrasing queries. But caching across matters risks leaking one client's confidential facts into another's results via a cache hit. The cache key includes `matter_id`; a query about *general, non-matter-specific* legal knowledge (jurisdiction-level statute questions, not tied to client facts) can be cached firm-wide, but anything touching matter-specific documents is scoped to that matter's cache namespace only.
- **KV/prefix caching:** the firm's legal writing style guide and standard research-memo format sit as the static prompt prefix across all 50,000+ monthly research queries — high-volume, high-leverage given the module's point that stable-prefix savings compound at production volume.

**Graceful degradation design:**

- Research and drafting are independently feature-flagged — if a data quality issue affects drafting output quality, it can be disabled while research keeps operating.
- Circuit breaker at the gateway watches the Azure AI Foundry error rate/latency and trips to the "keyword search only" / "manual drafting only" fallback automatically rather than letting individual requests fail one at a time during an outage.
- Aderant is architecturally outside the AI system's failure domain entirely — it's a sidecar consumer of attribution metadata, never a caller into or dependency of the AI path, so "the system must not interrupt the billing workflow if the AI is unavailable" is true by construction, not by exception handling.

### Section 4 — Data Pipeline

**Pipeline stages (source → processing → AI layer):**

1. **Source connectors:** iManage REST API (case files, correspondence, memos — 10 years of history) is the primary content source; Aderant Expert is queried for matter/client/billing-code metadata used for validation and attribution, not indexed as retrievable content itself.
2. **Document parsing:** extract text from Word documents, PDFs, and email correspondence stored in iManage — legal documents frequently carry tracked changes and comments, which need to be resolved to final text (or explicitly excluded) rather than ingested as noisy raw markup.
3. **Preprocessing:** deduplicate near-identical draft versions of the same document (iManage's own versioning creates many similar copies), strip standard confidentiality footers and email signature blocks, extract and attach metadata: `matter_id`, `document_type`, `date`, `author`, and — critically — the **matter-level ACL** from Azure AD, attached to every chunk at ingestion time.
4. **Chunking:** legal documents are chunked along clause/section boundaries rather than fixed token windows, so a retrieved chunk is a coherent contractual provision rather than a mid-clause fragment.
5. **Embedding and indexing:** chunks are embedded and written to the vector index with the matter ACL metadata carried through — retrieval at query time filters by the requesting attorney's authorized matters *before* similarity ranking, not after, so an unauthorized document can never appear in a result set to be later filtered out.

**Freshness SLAs:**

| Data source | Freshness SLA | How enforced |
|---|---|---|
| iManage documents (new filings, correspondence, drafts) | ≤ 24 hours | Nightly incremental update using iManage's document version/last-modified timestamps — appropriate because legal research isn't typically minute-sensitive, and full corpus re-ingestion at this volume would be wasteful |
| Aderant matter status and ACLs | ≤ 15 minutes | Scheduled poll — matter status (open/closed) and attorney entitlements must be close to current, because a matter closed or an attorney removed from it should promptly stop being queryable |

**Staleness detection:**

Document staleness: compare the iManage version/last-modified timestamp recorded at ingestion against iManage's current metadata for that document; if a retrieved chunk's source has since been superseded by a newer version, the research memo appends an explicit notice ("this document has been updated in iManage since it was last indexed — verify the current version before relying on it"). Authorization staleness is treated more strictly than content staleness: if a matter has been closed or an attorney's entitlement revoked since the last ACL sync, the system fails closed (denies the query) rather than serving a result based on a possibly-stale authorization state — the asymmetry is deliberate, because a stale "yes" on document freshness is a quality issue, while a stale "yes" on authorization is a privilege breach.

## Scenario C — RetailMind: E-Commerce Platform Integration

**Recap of scenario facts used below:** PIM (8M SKUs, REST API + Kafka product-change topic), CDP (purchase history, browsing behavior, session data), OMS, Elasticsearch (existing keyword search, not replaced), AWS/ECS microservices. From the Module 3 memo this design continues: ShopSphere, 15M registered users, 2M DAU, GDPR applies to EU users, the recommendation/search surface drives 35% of purchases, Black Friday peak is 5× normal load.

### Section 1 — Integration Layer Design

**Gateway design and rationale:**

This is the closest match to the course's own cloud-native case study: two AI features (conversational search, shopping assistant) built by what are effectively two different product teams, running on shared AWS/ECS infrastructure. The right pattern, directly from that case study, is **one shared LiteLLM proxy deployed as its own ECS service**, giving both teams a single integration point with per-feature cost attribution and per-feature rate limits.

The rate-limiting function matters more here than in either other scenario because of the Black Friday constraint: at 5× normal load, if the shopping assistant's tool-calling logic misbehaves (e.g., a retry loop against the PIM), it must not be able to exhaust shared AI capacity and starve conversational search — which sits on the critical path of a surface that drives 35% of purchases. A gateway with per-feature quotas is what makes that isolation possible; without it, both features share fate under load.

Routing is also doing real work here, not just abstraction: conversational search needs a small, fast, cheap model for query-to-filter parsing, while the shopping assistant needs a larger, more capable model for multi-turn reasoning and tool orchestration. The gateway routes each feature to its appropriate model tier by request type — a routing decision, not just a pass-through.

**Adapter interface contract:**

```
interface SearchAssistantAdapter {
  parseSearchQuery(request: SearchParseRequest): Promise<StructuredFilters>
  assistantTurn(request: AssistantTurnRequest): Promise<AssistantTurnResponse>
}

SearchParseRequest {
  raw_query: string
  session_context: object   // recent filters, category if browsing within one
}

StructuredFilters {
  category: string | null
  price_min: number | null
  price_max: number | null
  brand: string[] | null
  attributes: object
  sort: string | null
  confidence: number
  fallback_used: boolean    // true if AI parsing failed and raw query passed through
}

AssistantTurnRequest {
  conversation_id: string
  user_message: string
  session_context: object   // from CDP: recent views/purchases, for personalization
}

AssistantTurnResponse {
  message: string
  tool_calls: [{ name: string, arguments: object, result: object }]
  recommended_products: [{ sku: string, name: string, price: number, in_stock: boolean }]
}
```

Both features call this adapter regardless of which model handles parsing versus assistant turns — the search and catalogue services never call the gateway or a provider SDK directly, only this interface.

**Request/response pattern for each AI feature, with justification:**

| Feature | Pattern | Justification |
|---|---|---|
| Conversational search query parsing | **Synchronous, no streaming** | The output is small and structured (a filter object, not prose) and feeds directly into an Elasticsearch call that the user is waiting on as part of a single page load. There's nothing to stream — the whole point is a fast, complete structured object handed to ES. |
| Shopping assistant | **Synchronous with streaming**, with mid-turn tool calls to PIM/OMS for live product data | This is a genuinely conversational, multi-turn UI — users expect a chat-like experience, so streaming keeps perceived latency low even though a turn involving tool calls can take several seconds end-to-end. |

### Section 2 — Output Handling Strategy

**Output schema (for each AI feature):**

```json
// Conversational search
{
  "original_query": "string, required",
  "filters": {
    "category": "string or null",
    "price_min": "number or null",
    "price_max": "number or null",
    "brand": "array of string or null",
    "attributes": "object",
    "sort": "string or null"
  },
  "confidence": "number, 0-1",
  "fallback_used": "boolean, required"
}

// Shopping assistant
{
  "conversation_id": "string, required",
  "turn_id": "string, required",
  "message": "string, required",
  "tool_calls": [
    { "name": "string", "arguments": "object", "result": "object" }
  ],
  "recommended_products": [
    { "sku": "string, matches PIM SKU pattern", "name": "string", "price": "number", "in_stock": "boolean" }
  ]
}
```

**Validation layers:**

| Layer | What it checks | Example failure |
|---|---|---|
| Schema validation | `filters` object matches the shape the Elasticsearch query builder expects; `sku` values match the PIM SKU format; `price` fields are numeric | Assistant returns a `sku` value that isn't in valid PIM format — rejected before being surfaced as a "recommended product" |
| Semantic validation | `price_min` is not greater than `price_max` (a nonsensical range that passes schema validation); the assistant's stated price/availability in `recommended_products` must match the *live tool-call result verbatim* — the model is not permitted to restate a price or stock status from memory, only from the tool response just returned | Assistant recalls a price from earlier in the conversation instead of the current tool-call result — flagged as a potential staleness/hallucination and overwritten with the live value before the message is shown |
| Business rule validation | A recommended product must currently be in stock per OMS, or explicitly marked backorderable; a search filter category must exist in the current PIM taxonomy; the assistant may not reference competitor retailers or promise discounts outside the active promotions table | Assistant recommends a SKU that OMS reports as out of stock with no backorder flag — swapped for an in-stock alternative before the response reaches the user |

**Fallback chain:**

| Failure mode | Fallback behaviour |
|---|---|
| AI unavailable | Conversational search: the raw query string is passed directly to Elasticsearch as a keyword search — the exact pre-AI behavior, so "product search must still work" holds by construction, not as a special case. Shopping assistant: the chat entry point is hidden via feature flag; users fall back to standard browse/filter/search UI. |
| Schema validation failure | Retry with clarification, 1–2 attempts. If still failing: search falls back to the same raw-keyword-to-ES path as the unavailable case; the assistant returns a degraded response ("Let me search for that instead") and runs a plain keyword search on the user's last message rather than attempting further structured tool orchestration. |
| Business rule failure after retries | Search: filters that fail business rules (e.g., an invalid category) are dropped, and the query proceeds to Elasticsearch with the remaining valid filters plus the raw query text as a backup signal, rather than returning zero results. Assistant: a repeatedly out-of-stock recommendation is replaced with ranked in-stock alternatives sourced from the existing (non-AI) recommendation ranking, with a brief note, rather than surfacing the AI's original suggestion. |

### Section 3 — Non-Functional Requirements

**Latency budget:**

| Feature | P50 | P95 | Consequence of missing budget |
|---|---|---|---|
| Conversational search parsing | 150ms | 450ms | This sits inside an overall page-load budget alongside the Elasticsearch call itself; if the AI parsing step alone approaches or exceeds ~450ms, the gateway times the call out and the query falls straight to the raw-keyword fallback (Section 2) rather than delaying page render — the user experience degrades to "less smart search," never to "slow search." |
| Shopping assistant turn (incl. tool calls) | 1.5s to first token | 5s to complete turn | Streaming means the user sees a response starting well before the full turn, including any tool-call round-trips, completes; tool calls themselves (fast internal REST/cache lookups against PIM/OMS, not further LLM calls) are budgeted at P95 200ms each so they don't dominate the turn latency |

**Caching approach:**

- **Exact-match cache** for conversational search: e-commerce query distributions are famously head-heavy — a small set of popular queries accounts for a large share of volume — which is exactly the condition under which exact-match caching earns its keep. Cache key: normalized query text + active category context; short TTL (e.g., 15 minutes), shorter than the catalogue freshness SLA below, because a parsed filter combined with a price threshold can shift meaning if inventory or pricing moves.
- **Semantic cache** for phrasing variants of the same intent ("cheap running shoes" vs. "affordable running shoes"). Given the concentrated, head-heavy query distribution here, targeting a hit rate in the 30–45% range (consistent with published production benchmarks for this pattern) is a reasonable design target, with the similarity threshold tuned empirically against ShopSphere's actual query logs rather than set by intuition.
- **KV/prefix caching:** the static system prompt (parsing instructions, the PIM category taxonomy reference used to ground category names) is the stable prefix for both features; the variable user query or conversation turn is appended after it.
- Deliberately **not cached:** live price/availability data returned via tool calls — caching that would reintroduce exactly the staleness risk the tool-call design exists to avoid.

**Graceful degradation design:**

- Circuit breakers on both features independently. During the Black Friday 5× peak, the breaker on the shopping assistant can trip (degrading to the standard browse UI) while conversational search — the higher-traffic, more revenue-critical surface — keeps operating, because the two are isolated at the gateway rather than sharing a single fail-together path.
- Feature flags allow disabling the assistant entirely while keeping conversational search live, or reverting conversational search fully to plain Elasticsearch keyword matching if the parsing service itself degrades — this is possible specifically *because* the AI layer was designed from the start as a layer in front of Elasticsearch, not a replacement for it.
- The core keyword-search path (pre-AI Elasticsearch) is kept "always warm" as the permanent fallback target for both features, rather than being a legacy path that atrophies once the AI layer ships — it is deliberately still the production fallback, always tested, not a museum piece.

### Section 4 — Data Pipeline

**Pipeline stages (source → processing → AI layer):**

1. **Event-driven ingestion:** a Kafka consumer subscribes to the PIM's product-change topic (price updates, new SKUs, discontinued items, spec/attribute changes) — this is the mechanism that meets the "propagate within 5 minutes" requirement, since scheduled batch re-ingestion at any reasonable interval would either miss the SLA or be wastefully frequent for 8M SKUs.
2. **Preprocessing:** normalize raw PIM attribute names into the canonical vocabulary the assistant's tool-call schema and the search-parsing model's category grounding expect (e.g., mapping varied internal attribute keys to consistent "color," "size," "material" fields).
3. **Two distinct downstream targets, not one:**
   - **Taxonomy/attribute grounding store** (small, embedded, re-embedded incrementally as changed terms arrive) — used only to help the query-parsing model map natural language to valid categories and attributes. This is the piece with the 5-minute freshness SLA.
   - **Live tool-call path** for price, availability, and specifications — the shopping assistant's tool calls hit PIM/OMS (or a very short-TTL cache, seconds not minutes) directly at request time. This deliberately bypasses the ingested/embedded store entirely, because the worksheet's own requirement — "live product data via tool calls" — means these fields must never be served from a pipeline-fed copy that could be minutes stale, especially for a checkout-adjacent decision like availability.
4. **CDP data** (purchase history, browsing behavior) feeds the shopping assistant's personalization context via a separate, lower-urgency batch sync, since a slightly stale personalization signal degrades gracefully (a mildly outdated "recently viewed" list is a UX nit, not a correctness problem).

**Freshness SLAs:**

| Data source | Freshness SLA | How enforced |
|---|---|---|
| PIM catalogue/taxonomy (for query-parsing grounding) | ≤ 5 minutes | Kafka event-driven incremental update from the product-change topic |
| Price / availability / specifications (shown to users, used in recommendations) | Real-time (live at request time) | Direct tool call to PIM/OMS per assistant turn, bypassing the batch/embedded pipeline entirely; a seconds-level cache at most, for burst protection during peak load |
| CDP behavioral data (personalization context) | ≤ 1 hour | Scheduled batch sync; acceptable staleness given the non-critical nature of personalization context |

**Staleness detection:**

Kafka consumer lag is monitored directly and is the primary staleness signal for the taxonomy/grounding store: if lag implies the 5-minute SLA is at risk, an alert fires, and — because price/availability is never sourced from this pipeline — the actual purchase-blocking data (what a user sees as "in stock, $49.99") is never at risk from this particular failure mode, only the quality of query understanding is. For the live tool-call path, staleness in the traditional sense doesn't apply since it's always fetched fresh; the equivalent risk is a tool-call timeout or failure, which is monitored separately and, per the fallback chain in Section 2, results in the assistant telling the user it can't confirm current availability rather than guessing from a cached or remembered value.

## Rubric Commentary

**Gateway justification:** A good answer explains why a gateway earns its place in *this* scenario's specific constraints, not a recitation of the generic feature list. In Scenario A, the justification is multi-site rate limiting on a fixed self-hosted GPU allocation and centralized PHI redaction — not "gateways are good practice." In Scenario B, it's the matter-level authorization enforcement the worksheet explicitly demands, which has to live somewhere structural rather than in every calling service. In Scenario C, it's protecting one feature's Black Friday traffic spike from starving the other feature's shared capacity. A common mistake is to justify the gateway entirely in terms of model-swapping flexibility while ignoring the scenario's actual pressure point (data residency, authorization, or shared-capacity isolation).

**Adapter interface:** Good answers define an interface application services call that has no model name, no provider SDK type, and no raw prompt string in its signature — only domain-shaped inputs (`encounter_id`, `matter_id`, `raw_query`) and outputs. A common mistake is to define the "adapter" as a thin wrapper that still leaks the underlying provider's request/response shape, which means a model swap still touches every caller — defeating the entire point of the pattern. Scenario B's adapter is the clearest test case: if the authorization check isn't inside the adapter boundary itself (rather than "the caller is supposed to check first"), the interface hasn't actually enforced anything.

**Output schema completeness:** All three scenarios need explicit non-empty-string and referential-integrity checks (a `matter_id` that must resolve to something real, a `sku` that must match a real format) in schema validation, a domain-specific "does this make sense" check in semantic validation (a hallucinated medication, a citation-free legal memo, a price the model recited from memory instead of the live tool result), and a rule that only someone who knows the business could write in business-rule validation (formulary thresholds, cross-matter privilege, in-stock status). A common mistake is collapsing semantic and business-rule validation into one layer — the module treats them as separate for a reason: semantic validation asks "does this make sense in general," business-rule validation asks "does this comply with rules specific to us," and conflating them tends to mean the business-rule layer never gets written at all.

**Fallback specificity:** Good answers name what happens, concretely, for every listed failure mode — and Scenario C is the sharpest test, because "product search must still work" only holds if the fallback is *literally* the pre-AI keyword search path, not a vaguer "show an error and let the user retry." A common mistake across all three scenarios is writing a fallback chain that handles "AI unavailable" well but goes vague on "business rule failure after retries" — treating it as an edge case rather than, in Scenario B's case, a privilege-boundary security event that needs its own escalation path distinct from an ordinary retry-then-give-up flow.

**Latency design:** Every scenario needs P95 (or P99), not just P50, and the target has to be justified by what's actually on the critical path. Scenario A's async note generation correctly has a *minutes*-scale SLA because nothing about it blocks the clinical encounter; Scenario C's search-parsing step correctly has a *sub-second* SLA because it sits inside a page load. A common mistake is applying one latency mental model uniformly — either treating everything as needing sub-second sync latency (ignoring that async features don't need it) or treating everything as safely async (missing that Scenario C's search parsing genuinely is latency-critical because it's embedded in a synchronous page render).

**Data pipeline freshness:** The rubric row asks for freshness SLAs "per source," and the scenarios are designed so that a single blanket SLA is visibly wrong for at least two sources in every case. Scenario C is the clearest: the PIM taxonomy has a 5-minute event-driven SLA, but price/availability isn't on a freshness SLA at all — it's live, fetched at request time, specifically because 5 minutes is too stale for a number a customer might buy against a second later. A common mistake is applying the RAG-pipeline mental model (chunk, embed, index, set one staleness clock) even to data that shouldn't go through a batch pipeline at all — Scenario C's live tool-call path and Scenario A's live FHIR context fetch are both cases where the correct architectural answer is "this data source doesn't get a freshness SLA in the ingestion-pipeline sense, because it's never ingested — it's fetched live," and an answer that force-fits every data source into "chunk it and set a re-embedding cadence" has missed that distinction.

**Overall quality signal (the 2am test):** In all three scenarios, the test resolves the same way by design: HealthBridge physicians keep charting if the self-hosted model is down; Meridian attorneys keep searching iManage by keyword and drafting from templates if Azure AI Foundry is unreachable; ShopSphere customers keep searching and buying if the AI gateway is down, because the underlying systems (Epic, iManage, Elasticsearch) were never made dependent on the AI layer's availability. A model answer that requires "the AI catches back up" or "queued requests get replayed" before the product is usable again has failed this test, regardless of how complete the other four sections look.
