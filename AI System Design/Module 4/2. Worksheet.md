## Scenario Options

### Scenario A — HealthBridge: EHR Integration

HealthBridge has approved the clinical documentation AI system (designed in Module 3). The AI generates SOAP-format clinical note drafts from encounter transcripts. Now you need to integrate it with their existing infrastructure.

Existing systems: Epic EHR (FHIR R4 API for reading patient context and writing completed notes), a speech-to-text transcription service (Azure AI Speech, already deployed), an encounter scheduling system (Epic, read-only access), and a clinical staff authentication system (Azure AD). The AI model runs self-hosted on HealthBridge infrastructure.

Integration requirements: the transcription output must flow to the AI note generator automatically at encounter end; the AI draft must surface in Epic for physician review before any data is written; the physician's approval action in Epic triggers the write. PHI must not appear in any log without redaction. The system must degrade gracefully if the AI is unavailable — encounters still happen; notes still get written manually.

### Scenario B — LexAI: iManage Integration

Meridian & Partners has selected their model approach (from Module 3). Now you need to wire the AI research and drafting system into their existing law firm infrastructure.

Existing systems: iManage Work 10 (the firm's document management system — case files, correspondence, and memos all live here; it has a REST API), Aderant Expert (practice management and billing system — matter numbers, client IDs, billing codes), Microsoft 365 (email and document editing for attorneys), and the firm's identity provider (Azure AD, with matter-level access controls). The AI research system queries iManage; the AI drafting system writes draft documents back to iManage.

Integration requirements: attorney queries must be scoped to matters they are authorised to access — the integration must enforce this, not just the UI. Drafted documents must be saved as a new iManage version, not overwrite originals. All AI queries and responses must be logged with the matter number for billing attribution. The system must not interrupt the billing workflow if the AI is unavailable.

### Scenario C — RetailMind: E-Commerce Platform Integration

ShopSphere has selected their model approach (from Module 3). Now you need to integrate the conversational search and shopping assistant AI into their cloud-native e-commerce platform.

Existing systems: a product information management system (PIM — source of truth for 8M SKUs, with a REST API for product data and a Kafka topic for product change events), a customer data platform (CDP — purchase history, browsing behaviour, and session data), an order management system (OMS), and an Elasticsearch cluster currently powering keyword search. The engineering team runs on AWS; the platform is microservices on ECS.

Integration requirements: the conversational search AI parses natural-language queries and passes structured filters to Elasticsearch — it does not replace Elasticsearch. The shopping assistant needs access to live product data (price, availability, specifications) via tool calls. Product catalogue changes must propagate to the AI layer within 5 minutes. All AI features must have defined fallback behaviour when the AI is unavailable — product search must still work.

## Self-Assessment Rubric

| Criterion | What good looks like | ✓ / ✗ |
|---|---|---|
| Gateway justification | Explains why a gateway rather than direct SDK calls — not just "we need a gateway" | |
| Adapter interface | Stable contract defined; the model can be swapped without changing consuming services | |
| Output schema completeness | All three validation layers addressed with scenario-specific examples | |
| Fallback specificity | Every AI touch point has a named fallback behaviour — not "returns an error" | |
| Latency design | AI latency treated differently from DB latency; P95 targets set, not just P50 | |
| Data pipeline freshness | Freshness SLAs defined per source; staleness is detectable, not invisible | |

**Overall quality signal:** If the AI component were disabled at 2am, would the product still function for users? If your architecture ensures yes, the integration is production-grade.
