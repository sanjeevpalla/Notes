## Scenario A — HealthBridge: Clinical Documentation AI

### Section 1 — Five-Dimension Framework

**Task capability fit:**
This is a long-form generative task — transforming 15–45 minutes of diarised encounter transcript into a structurally consistent SOAP note with correct clinical terminology — not a retrieval or classification task. The model needs strong instruction-following over long context, reliable structured-output adherence (four sections, every time), and accurate use of medical vocabulary. A frontier-tier model would clear this bar out of the box; a fine-tuned mid-tier open-weight model can also clear it, because this is precisely the style/format-plus-domain-vocabulary combination fine-tuning is good at, and format consistency is not negotiable here — a mid-tier model reaching frontier-adjacent quality on this one narrow task at a fraction of the ongoing dependency is the more defensible target.

**Latency profile:**
This is not a real-time interactive use case — the transcript exists only after the encounter ends, so processing is asynchronous by nature. But "asynchronous" is not "unbounded": physicians are time-pressured and the draft needs to be ready before they move to the next patient or close out their charting for the day, not sometime overnight. Target: a complete draft SOAP note within 90 seconds of transcript availability. That target is comfortably achievable async and does not require the fastest tier; it does rule out designs with unpredictable queueing delay.

**Cost at scale:**
Launch volume (2,000 encounters/day) and 18-month volume (10,000/day) both sit well below the 500K–5M requests/month crossover range this module uses for API-vs-self-host comparisons (60,000/month at launch, 300,000/month at 18 months). At this volume, a raw token-cost comparison would favor an API. That comparison is academic here, because the next dimension removes the API option before cost gets a vote — the cost model still has to be built and shown, but its role in this memo is to quantify the price of the compliance requirement, not to select the model.

**Data privacy posture:**
Non-negotiable, and the deciding dimension. All encounter data is PHI under HIPAA, and the scenario states plainly that data cannot leave the HealthBridge private cloud — not "may leave under a data-use agreement," as some HIPAA-covered workloads allow via a Business Associate Agreement with a cloud provider, but a harder boundary: it stays inside HealthBridge's own cloud tenancy. Any candidate that sends data to a third party's general-purpose API infrastructure is disqualified regardless of capability or cost.

**Operational complexity:**
This is the dimension that keeps this scenario from being a copy of the module's healthcare case study. HealthBridge has a cloud infrastructure team — competent at running cloud workloads generally — but no ML engineering capability. A fully self-hosted, from-scratch fine-tuning and serving stack (GPU fleet, vLLM or an equivalent serving layer, a training and evaluation pipeline, ongoing re-fine-tuning as the base model updates) is a materially different discipline than what this team currently runs, and understaffing this is the single most likely way this project quietly fails after a successful pilot.

### Section 3 — Fine-Tune vs. Prompt Engineering

**Recommendation: fine-tune, specifically for style/format consistency and domain vocabulary.**

This is squarely inside the fine-tuning value matrix from Lesson 3, on two of its four axes at once. First, format: a SOAP note is a rigid four-part structure that must hold across an enormous variety of encounter content — exactly the "large, diverse input space needing consistent behaviour" signal that Lesson 2 names as a prompt-engineering ceiling. Second, domain vocabulary: incorrect medical terminology in a clinical note is not a style defect, it's a patient-safety and billing problem, which is the domain-vocabulary case the course treats as a fine-tuning candidate almost by definition, not a borderline call.

What to fine-tune for: format and vocabulary, not knowledge. The model does not need to "know" HealthBridge's patients — the entire content it needs is in the transcript handed to it at inference time. This is worth stating explicitly because it's the most common failure mode this module warns about: nobody should be fine-tuning this model expecting it to recall prior encounters or hospital policy from training data. If a future capability needs that (e.g., surfacing a patient's relevant history), that is a RAG problem layered on top, not a reason to change the fine-tuning objective.

Data: LoRA adapter trained on de-identified historical transcript-and-note pairs, curated from HealthBridge's own prior documentation (physician-authored notes serve as the ground truth), not gathered from scratch. Recommend curating 1,500–3,000 clean pairs spanning HealthBridge's specialty mix, held out 15% for evaluation, with a physician-review panel calibrating the evaluation rubric — this is a case where automated metrics alone (ROUGE-style overlap) are not sufficient, per the module's evaluation-strategy guidance; physician sign-off on a representative sample is required before launch.

Establish the prompt-engineering baseline first, per the module's own anti-pattern warning (Lesson 6, anti-pattern three): before committing to the fine-tune, run the best achievable system prompt with few-shot SOAP examples against the same held-out set and measure its format-compliance and terminology-accuracy rate. Fine-tuning is justified only if it clears that baseline by a margin worth the ongoing maintenance obligation described in Section 4.

### Section 4 — Build/Buy/Open-Weight Recommendation

**Recommendation:**
Deploy a fine-tuned mid-tier open-weight model via a managed cloud AI platform (e.g., the kind of in-tenancy offering described in Lesson 4 — AWS Bedrock, Azure AI Foundry, or Google Vertex AI class of product), hosted inside HealthBridge's own cloud tenancy under a Business Associate Agreement, rather than building a fully self-hosted GPU stack from zero.

**Primary drivers:**
Data privacy is the dominant driver — the platform's data-use commitments and tenancy isolation satisfy "does not leave the private cloud" without a general-purpose third-party API in the loop. Operational complexity is the second driver, and the one that distinguishes this recommendation from a naive reading of the module's healthcare case study: HealthBridge's cloud infrastructure team can operate within a managed platform (configuration, monitoring, IAM) but does not yet have the ML engineering capability to run GPU serving, fine-tuning pipelines, and model evaluation from scratch. The managed platform converts a capability HealthBridge doesn't have (MLOps) into one it already has (cloud operations).

**Accepted risk:**
The team is still new to operating any AI system, managed platform or not — configuring the fine-tuning job, running the evaluation pipeline, and interpreting drift signals is new work even with GPU operations abstracted away. Recommend an initial build-and-transfer engagement: bring in external ML engineering support to stand up the fine-tuning pipeline and the first production deployment, with an explicit knowledge-transfer plan and a declining external-support budget over the first two quarters, so the capability genuinely lands with HealthBridge's own team rather than becoming a permanent external dependency. This is a real risk being accepted, not a solved one — see Section 6.

### Section 5 — Cost Model

**Assumptions:**
Average transcript length 20–25 minutes → roughly 4,500 input tokens (ASR transcript plus encounter metadata and a fixed system-prompt overhead); output SOAP note averaging 700 tokens. Frontier-tier illustrative pricing: $3/1M input, $15/1M output. Self-hosted/managed-platform infrastructure: mid-tier open-weight model, GPU instance cost ~$6/hour, running continuously (730 hours/month). Scenario A specifies an 18-month projection (10,000 encounters/day) rather than the generic 12-month horizon most scenarios use; that figure is used directly below rather than substituted with a 12-month guess.

**Launch scale — monthly cost (2,000 encounters/day → 60,000/month):**
Illustrative frontier-API-equivalent cost (shown for comparison, not proposed): 60,000 × ((4,500 × $3/1M) + (700 × $15/1M)) = 60,000 × $0.024 = **$1,440/month**.
Recommended path: 2 GPU instances × $6/hour × 730 hours = $8,760/month infrastructure, plus an estimated $15,000/month external MLOps/knowledge-transfer support during the initial build phase = **≈$23,760/month**.

**18-month scale — monthly cost (10,000 encounters/day → 300,000/month):**
Illustrative frontier-API-equivalent: 300,000 × $0.024 = **$7,200/month**.

**Crossover point:**
Cost alone does not favor self-hosting or the managed platform at either scale — the recommended path runs roughly 16.5× the illustrative API-equivalent cost at launch, narrowing to roughly 3.5× by 18 months as fixed infrastructure and MLOps costs are spread across a growing volume. HealthBridge never reaches the 500K–5M requests/month range where self-hosting or an in-tenancy platform would win on cost alone. State this plainly to leadership: this is the price of the privacy requirement, not a sign the model choice is wrong, and it is a price that shrinks — not grows — as the deployment scales toward its 18-month target.

### Section 6 — Primary Risk

The recommendation assumes HealthBridge's cloud infrastructure team fully absorbs ongoing model operations — monitoring, drift detection, and periodic re-fine-tuning when the underlying base model is updated — after the initial external engagement winds down. This is the single assumption most likely to be wrong. If the knowledge transfer is incomplete, the fine-tuned adapter can drift quietly out of alignment with a new base model version (the ongoing-maintenance problem the module names directly), and there is nobody in-house yet who reliably detects that before it shows up as a real quality regression in physician-facing output — which, for a legal clinical document, is a much more serious failure mode than a typical production bug.

What to monitor: physician edit-distance between the AI draft and the final signed note, tracked weekly from week one to establish a baseline, with an alert if the rate rises more than roughly 20% relative to that baseline; and a quarterly checkpoint, owned jointly by HealthBridge and the external engagement partner, confirming HealthBridge staff can independently run the evaluation pipeline against a held-out sample — not just that the system is working, but that HealthBridge could tell if it stopped.

## Scenario B — LexAI: Legal Research and Drafting

### Section 1 — Five-Dimension Framework

**Task capability fit:**
The two sub-tasks need different things from a model, which matters for every dimension below. Research synthesis needs the model to reason accurately over retrieved case-file content and produce a structured memo without fabricating a citation — a reasoning-over-retrieved-content task, not a knowledge-recall task, since the case files themselves are external content the model must be handed, not something baked into its weights. Drafting needs consistent adherence to the firm's house style and document conventions — closer to a format/style problem. Frontier-tier capability is justified for both given the malpractice exposure of a wrong legal conclusion or a fabricated citation; this is not a task where trading capability for savings is worth the risk at the firm's current volume.

**Latency profile:**
Both sub-tasks are asynchronous — a research memo or a first-draft document delivered within a few minutes is well within what an attorney expects, nothing here resembles a real-time chat interface. This is a genuinely low-stakes dimension for LexAI, which frees weight to be allocated to the dimensions that actually decide the case.

**Cost at scale:**
50,000 searches and 5,000 drafting tasks per month is modest volume — nowhere near the 500K–5M requests/month range where self-hosting starts to win on cost. At this volume, the per-token cost difference between paying for frontier-tier quality and trying to save money on a smaller tier is small in absolute dollar terms relative to the billable-hour savings the firm is trying to prove to skeptical partners; this is a scenario where under-investing in capability to save a few hundred dollars a month is a bad trade.

**Data privacy posture:**
Attorney-client privilege is the central constraint, but it is a conditional one, not an absolute one like HealthBridge's: client matter data cannot transit to any third-party system without explicit client consent. That opens a real design choice — a managed cloud platform under an enterprise agreement with explicit no-training, limited-retention data-use terms materially changes what "transits to a third party" means in practice, compared to sending data to a vendor's standard commercial API with default retention terms. The default posture, absent consent, should assume the strictest reading: matter data should only go to a system with contractual protections at least as strong as a data-processing addendum with no-training and short-retention guarantees.

**Operational complexity:**
This is the dimension that decides the scenario. A 3-person IT team supporting 200 attorneys has no spare capacity for GPU fleet management, a fine-tuning pipeline, or an evaluation program — that's not a judgment about the team's competence, it's an arithmetic fact about headcount. Any candidate requiring self-hosted infrastructure is very likely to fail on this dimension alone, independent of how well it scores elsewhere.

### Section 3 — Fine-Tune vs. Prompt Engineering

**Recommendation: prompt engineering as the ceiling, for both sub-tasks, at current scale.**

Research synthesis is a knowledge-and-retrieval problem, not a behaviour problem — the model needs the firm's case files handed to it as retrieved context (RAG), which is a different architectural decision from fine-tuning entirely. The module's decision guide is explicit here: needing the model to know proprietary documents points to RAG, not fine-tuning. Fine-tuning a model on the firm's case files would not make it reliably recall specific case details at inference time — it would make it sound like the firm's case files while still needing to be handed the actual content to reason over accurately. That would be the module's most common fine-tuning mistake, applied to a law firm's most sensitive data.

Drafting is closer to a legitimate style/format fine-tuning candidate on paper — Meridian does have a decade of internally drafted documents that could, in principle, teach a model the firm's house style, the same "labels as a by-product of work already done" pattern the module's fintech case study describes. That is a genuine future option worth flagging, not dismissing. But it is the wrong first move for this firm specifically: at 5,000 drafting tasks/month, and with a 3-person IT team that has no capacity to run a fine-tuning and evaluation pipeline, the honest application of the module's own ceiling test — "have you genuinely hit the ceiling, or does it just feel easier to fine-tune?" — comes back negative. Nobody has yet tried a well-engineered system prompt with the firm's own best past drafts as few-shot exemplars and measured where it falls short.

What would signal the ceiling has actually been reached: format or clause-structure violations that persist despite iterating on the prompt across several drafting-task types; partners consistently editing the same category of stylistic issue regardless of prompt changes. Track this over the first two quarters. If it shows up, the firm now has a specific, evidenced case for revisiting fine-tuning for the drafting sub-task — and, unlike most teams reaching for fine-tuning, it will already have the prompt-engineered baseline on record to prove the investment adds value, satisfying the module's anti-pattern-three warning by construction rather than as an afterthought.

### Section 4 — Build/Buy/Open-Weight Recommendation

**Recommendation:**
Buy — a frontier-tier model accessed through a managed cloud AI platform or an enterprise API agreement with explicit no-training and limited-retention data-use terms, with research synthesis built as a RAG pipeline over the firm's 10 years of case files and drafting built as prompt-engineered generation using firm-specific templates and few-shot exemplars.

**Primary drivers:**
Operational complexity is the strongest driver — a 3-person IT team cannot run any self-hosted GPU infrastructure, full stop, which rules out the self-hosted candidate regardless of its other merits. Data privacy is the second driver, and it is why "buy" specifically means an enterprise agreement with contractual data-use protections rather than a default commercial API account — the distinction that separates the winning candidate from the runner-up in Section 2.

**Accepted risk:**
Even under a strong enterprise agreement, client matter data is still, in a technical sense, transiting to a third party — this does not fully eliminate the privilege question for the firm's most sensitive matters, only the routine ones. Recommend a carve-out: matters flagged by the assigning partner as highly sensitive (ongoing litigation with heightened confidentiality orders, matters explicitly excluded by client engagement letters) route to a separate, more conservative workflow — either an explicit client-consent step before AI assistance is used, or manual handling — rather than assuming the enterprise agreement is a blanket solution to privilege for every matter in the firm. Also build the integration behind a model-agnostic abstraction layer (an internal `complete(prompt, config) → response` interface, in the spirit of LiteLLM) from day one — with a 3-person team, a forced provider migration a few years from now, done without one, is exactly the kind of two-sprint scramble the module's vendor-lock-in anti-pattern describes, and this team has the least slack of any candidate in this document to absorb that scramble.

### Section 5 — Cost Model

**Assumptions:**
Research synthesis: RAG context of roughly 2,500 tokens (five retrieved case-file chunks at ~500 tokens each) plus query and system-prompt overhead, totaling ~3,000 input tokens; output memo averaging 900 tokens. Drafting: ~3,500 input tokens (matter context, template, few-shot exemplars); output draft averaging 2,200 tokens (a full contract or motion draft runs long). Frontier-tier illustrative pricing: $3/1M input, $15/1M output. Managed-platform fee: ~10% over raw token pricing. No explicit 12-month volume is given in the scenario; assume adoption grows from an initially skeptical rollout to firm-wide use, roughly 90,000 searches and 9,000 drafting tasks/month by month 12 — stated here as an assumption, not a scenario fact.

**Launch scale — monthly cost (50,000 searches, 5,000 drafting tasks):**
Research: 50,000 × ((3,000 × $3/1M) + (900 × $15/1M)) = 50,000 × $0.0225 = $1,125.
Drafting: 5,000 × ((3,500 × $3/1M) + (2,200 × $15/1M)) = 5,000 × $0.0435 = $217.50.
Subtotal: $1,342.50; with a 10% managed-platform fee: **≈$1,480/month**.

**12-month scale — monthly cost (assumed 90,000 searches, 9,000 drafting tasks):**
Research: 90,000 × $0.0225 = $2,025. Drafting: 9,000 × $0.0435 = $391.50. Subtotal: $2,416.50; with the 10% fee: **≈$2,660/month**.

**Crossover point:**
Not reached, and not close. Even at the assumed 12-month combined volume (~99,000 requests/month), LexAI sits well under a tenth of the 500K–5M requests/month range where self-hosting starts to compete on cost — it would take a five-to-fifty-fold increase in volume before the crossover math even becomes worth rerunning. Combined with the 3-person IT team's operational ceiling, this is not a decision that needs revisiting on any near-term horizon; it would take a change in firm size or IT staffing, not just usage growth, to change the recommendation.

### Section 6 — Primary Risk

The recommendation's biggest exposure is not technical capacity, it's the RAG pipeline's citation accuracy — specifically, the assumption that grounding the research-synthesis output in retrieved case-file chunks is sufficient to prevent fabricated citations. Retrieval reduces hallucination; it does not eliminate it, and a frontier model can still cite a case that was not actually in the retrieved set, or misstate a holding from a case that was. For a firm whose adoption already depends on skeptical partners' trust, one fabricated citation surfaced in front of a partner is plausibly enough to end the pilot regardless of how sound the rest of the architecture is.

What to monitor: an automated post-generation verification step that checks every case citation in a research memo against the chunks actually retrieved for that query, flagging any citation that doesn't trace back to a retrieved source before the memo reaches an attorney. Track the flag rate weekly; require human review of every flagged memo until the false-citation rate is measured, over a real sample, to be low enough that partners' trust in the system is based on evidence rather than optimism.

## Scenario C — RetailMind: Conversational Search and Shopping Assistant

### Section 1 — Five-Dimension Framework

**Task capability fit:**
The two capabilities need genuinely different things, which is the crux of this scenario. Conversational search — parsing a natural-language query into structured filters and a refined search query — is a narrow, well-bounded structured-extraction task, the kind of task the module treats as a strong task-specialisation fine-tuning candidate. The shopping assistant is the opposite shape: open-ended, multi-turn guided discovery over an 8M-SKU catalogue, which is a knowledge-and-reasoning task — the model needs to be handed relevant product information it doesn't have memorised (a RAG problem over the catalogue, not a fine-tuning-for-knowledge problem), and needs deeper reasoning to handle ambiguous, evolving user intent across turns than a single-shot query parse does.

**Latency profile:**
Both capabilities are real-time interactive, but with different tolerances. Conversational search sits in or near a search-as-you-type path — users expect a near-instant refinement, so time-to-first-token and total latency both need to stay in the low hundreds of milliseconds. The shopping assistant is a conversational back-and-forth where streamed, sub-two-second time-to-first-token feels responsive even if total generation takes longer — closer to a chat latency profile than a search one. This is also where the reasoning-mode dial from Lesson 1 matters: search-parsing needs none of it (it would only add latency and cost to a task that doesn't need deeper reasoning), while the assistant may warrant it selectively on genuinely ambiguous guided-discovery turns.

**Cost at scale:**
This is the dimension the scenario is built to stress-test, because the two capabilities sit at wildly different volumes and cost profiles. Search-parsing volume, driven by 2M DAU, runs into the hundreds of millions of requests per month — an order of magnitude or more above the 500K–5M crossover range, making self-hosting essentially mandatory on cost grounds alone for that capability specifically. Assistant volume is far lower (a fraction of DAU engage in guided discovery sessions) but each interaction carries more context and a higher capability requirement, so it sits in a different part of the cost/capability tradeoff entirely. Treating this as one blended cost model, rather than two, is the mistake to avoid.

**Data privacy posture:**
GDPR requires EU user data to stay within EU infrastructure — a residency requirement, not an absolute "must self-host everywhere" requirement like HealthBridge's. A managed cloud platform's EU region can satisfy this for the assistant capability without building an EU data centre from scratch; a self-hosted deployment can equally satisfy it by running EU-region instances. The requirement shapes where each capability's infrastructure lives, not which hosting model is chosen.

**Operational complexity:**
The inverse of the other two scenarios: ShopSphere's 50+ engineer team is a real operational asset, but the team has no prior AI system experience — the constraint is specific expertise, not headcount. This means self-hosting is operationally plausible here in a way it wasn't for HealthBridge or LexAI, but it should be phased: the team needs room to build AI-operations muscle rather than taking on two unfamiliar self-hosted stacks (a fine-tuned small model and a RAG-backed larger model) simultaneously on day one.

### Section 3 — Fine-Tune vs. Prompt Engineering

This scenario has two sub-capabilities with different, decisive answers — not a hedge, two resolved decisions.

**Conversational search parsing: fine-tune.** This is the module's standard high-volume, narrow-task play, and it fits almost exactly: a bounded output schema (structured filters), a consistent input shape (short natural-language queries), and volume high enough that the operational cost of fine-tuning is trivially justified by the savings at scale. Recommend the distillation pattern the module treats as the standard approach for exactly this shape of problem: use a frontier-tier model to generate teacher outputs (query → structured filter) on a large sample of ShopSphere's real historical search queries, verify a sample for quality, then fine-tune a small/fast open-weight model via LoRA on those input/teacher-output pairs. This pays frontier-tier prices once, at data-generation time, and serves at small/fast-tier prices indefinitely — the cost profile this task's volume specifically rewards. Check the frontier provider's terms of service before this becomes a core cost strategy, per the module's own caveat on distillation.

**Shopping assistant: prompt engineering as the ceiling, plus RAG over the product catalogue.** The assistant needs to know about 8M SKUs it cannot have memorised — a knowledge-injection need, which the module is explicit is a RAG problem, not a fine-tuning problem. Fine-tuning the assistant on product data would produce a model that sounds like it knows the catalogue while still hallucinating specifics, the module's most-named anti-pattern, applied to a capability that directly drives purchases. Start with a well-engineered system prompt (persona, guided-discovery conversation structure, constraints on what claims it can make about a product) plus RAG retrieval of the specific SKUs relevant to the conversation. Revisit fine-tuning only if a genuine ceiling signal appears — persistent tone or format violations despite prompt iteration — and even then, the fine-tuning objective would be conversational behaviour and format, not catalogue knowledge, which stays RAG's job regardless.

### Section 4 — Build/Buy/Open-Weight Recommendation

**Recommendation:**
A hybrid architecture: a fine-tuned small/fast open-weight model, self-hosted (EU-region and other-region instance pools), serving conversational search parsing; and a frontier-tier model, accessed via a managed cloud platform with an EU region for EU traffic, serving the shopping assistant with a RAG pipeline over the product catalogue — connected by a simple feature-level router (search traffic and assistant traffic are already distinct product surfaces, so no per-message classifier is needed here, unlike a general-purpose hybrid router).

**Primary drivers:**
Cost at scale is the dominant driver for the search-parsing decision — at 180M+ requests/month, this is deep into the range where self-hosting a small, fine-tuned model is unambiguously cheaper than any API-based option, independent of any other consideration. Task capability is the dominant driver for keeping the assistant on the frontier/managed-platform tier — open-weight models still show a real gap on open-ended, multi-turn reasoning, and with 35% of purchases running through this surface, trading capability for savings on the lower-volume, higher-stakes capability is the wrong trade.

**Accepted risk:**
Operating two model stacks (one self-hosted, one via managed platform) is more operational surface area than a single uniform approach, for a team that is strong generally but new to AI operations specifically. Mitigate by sequencing: stand up the self-hosted search-parsing stack first — the simpler of the two, and the one with the clearest cost justification — and use it to build in-house AI-operations experience before or alongside standing up the RAG-backed assistant on the managed platform. Also build both integrations behind a model-agnostic abstraction layer from day one; with two independently evolving model stacks, an OpenAI-compatible interface (LiteLLM or equivalent) is what keeps a future provider or tier change on one side of the hybrid from requiring a rewrite of the other.

### Section 5 — Cost Model

**Assumptions:**
Search parsing: ~3 calls per DAU session/day, ~150 input tokens, ~80 output tokens per call (structured JSON). Assistant: ~5% of DAU engage a guided-discovery session/day, ~6 turns/session, ~1,200 input tokens (conversation history plus ~8 retrieved SKUs at ~100 tokens each), ~250 output tokens per turn. Frontier-tier pricing: $3/1M input, $15/1M output. Self-hosted small/fast GPU instance: ~$2.50/hour, each instance sustaining ~350,000 requests/day at these token lengths (an assumption to validate via load testing, not a benchmarked figure). MLOps overhead for the self-hosted search stack: ~$20,000/month (shared, partial FTE allocation). Black Friday peak: 5× normal load, assumed to last ~4 days (96 hours) within the peak month. 12-month projection: DAU growing from 2M to an assumed 2.5M (25% growth) — a stated assumption, not a scenario fact.

**Launch scale — monthly cost (2M DAU, steady state):**
*Search:* 6M calls/day × 30 = 180M/month. Instances needed: 180M/30 days ÷ 350,000/day ≈ 18. Infra: 18 × $2.50 × 730 hrs = $32,850. Plus $20,000 MLOps overhead = **$52,850/month**.
*Assistant:* 100,000 sessions/day × 6 turns = 600,000 calls/day × 30 = 18M/month. Cost/call: (1,200 × $3/1M) + (250 × $15/1M) = $0.00735. 18M × $0.00735 = **$132,300/month**.
**Combined steady-state: ≈$185,150/month.**

*Black Friday peak add-on (within the launch-scale month):* Search peak (5×) needs ~86 instances; the extra 68 instances for ~96 hours add ≈$16,320. Assistant peak adds ~9.6M extra calls at $0.00735 ≈ $70,560. **Peak-month total: ≈$272,030.**

**12-month scale — monthly cost (assumed 2.5M DAU, steady state):**
*Search:* 7.5M calls/day × 30 = 225M/month. Instances: ≈22. Infra: 22 × $2.50 × 730 = $40,150 + $20,000 overhead = **$60,150/month**.
*Assistant:* 125,000 sessions/day × 6 = 750,000/day × 30 = 22.5M/month × $0.00735 = **$165,375/month**.
**Combined steady-state: ≈$225,525/month**, rising to roughly **$334,000** in a Black Friday month at this scale.

**Crossover point:**
Search-parsing volume (180M–225M/month) is an order of magnitude above the 500K–5M/month crossover range — this is not a close call, and it would remain self-hosted even under a large downward revision of the volume assumptions above. Assistant volume (18M–22.5M/month) is also numerically above that crossover range, but the task-capability gap discussed in Section 1 vetoes a pure cost-driven move to self-hosting for now, the same way HealthBridge's privacy requirement overrode a favorable cost signal in the opposite direction. Re-score the assistant capability against this framework every 6–12 months — the module notes the open-weight capability gap on complex reasoning is closing, and the assistant may become a legitimate self-hosting candidate before ShopSphere's next platform contract renewal.

### Section 6 — Primary Risk

The recommendation assumes the fine-tuned small/fast model for conversational search parsing will hold its accuracy as the catalogue evolves — new SKUs, new seasonal categories, shifting query patterns — without a deliberate retraining cadence keeping pace with that drift. This is the module's ongoing-maintenance risk applied to the highest-revenue-relevance capability in this memo: search quality on this surface is tied to 35% of purchases, and a fine-tuned classifier-shaped model degrades quietly, not with an obvious failure, when the distribution it was trained on drifts out from under it.

What to monitor: a rolling weekly evaluation of filter-parsing accuracy against a freshly labeled sample of real queries (not the original training-era eval set, which itself goes stale), with a drift alarm if accuracy drops more than a defined threshold relative to the post-launch baseline; and a re-fine-tuning cadence explicitly tied to catalogue change velocity — for example, after every seasonal catalogue refresh — rather than left to whenever someone notices a problem. Close the production feedback loop the module describes: log accepted-vs-corrected parsing outcomes in production and route corrected examples back into the training set, so the model is retrained against ShopSphere's actual, current query distribution rather than the one it launched on.

## Rubric Commentary

**Framework application:** Good answers make each of the five dimensions carry a scenario-specific number, constraint, or trade-off — not a restatement of what the dimension means in general. The tell is whether a sentence would survive being copy-pasted into a different scenario's memo unchanged. HealthBridge's operational-complexity analysis ("no ML engineering capability") could not be pasted into LexAI's memo without becoming false; that specificity is what the rubric is checking for. A common mistake is writing the data-privacy paragraph as "this is regulated, so privacy matters" — true of all three scenarios, and therefore not yet an analysis of any of them.

**Scorecard specificity:** Every score above carries a one-sentence reason tied to a fact from that scenario — not "5, because it's very capable." The weights matter as much as the scores: HealthBridge weights privacy at 30% because it's a hard constraint; LexAI weights operational complexity at 30% because of the 3-person IT team; RetailMind weights cost at 30% because of DAU-scale volume. A common mistake is using the same weight distribution across every project regardless of context, which produces a scorecard that always favors the same architecture — at which point it isn't doing any decision work.

**Fine-tune vs. prompt engineering:** The rubric explicitly flags "the domain is specialised, so fine-tune" as the failure mode to avoid, and this module gives you the tool to catch it: ask whether the need is knowledge (→ RAG) or behaviour (→ fine-tuning candidate), and whether a genuine ceiling has been measured or just assumed. LexAI's drafting sub-task is the clearest trap in this document — "legal drafting is specialised" sounds like a fine-tuning justification, but the correct answer at this firm's current scale and IT capacity is prompt engineering, with fine-tuning held as a future option contingent on an actual measured ceiling. RetailMind's two sub-capabilities land on opposite sides of this decision for legitimate, scenario-grounded reasons — that split is not a hedge, because each half is resolved decisively on its own terms.

**Recommendation clarity:** Each scenario states its recommendation in one sentence before the justification, and none of them resolve to "it depends" without resolution. RetailMind's is a hybrid, which sounds like a compromise but is not one: Lesson 4 treats the hybrid pattern as a specific, named architecture with its own justification, not an unresolved decision between two options. The common mistake this rubric row is catching is a memo that lists trade-offs for two pages and never states which one the architect is actually recommending.

**Cost model arithmetic:** All three memos show the multiplication, not just the answer, and name every assumption (token counts, per-token prices, instance costs, throughput-per-instance) before using it. HealthBridge's cost model is the instructive case here: the arithmetic shows self-hosting costing more than an API would at this volume, and the memo says so plainly rather than quietly picking numbers that make the preferred answer look cheaper. That honesty — showing a cost model that argues against your own recommendation on one dimension, then explaining why another dimension overrides it — is a stronger answer than a cost model engineered to agree with the conclusion. The common mistake this row is checking for is exactly Lesson 6's anti-pattern six: extrapolating a single pilot number linearly instead of separately modeling launch, growth, and (for RetailMind) peak.

**Risk specificity:** Each Section 6 names one specific, falsifiable assumption — not "the model might not perform well." HealthBridge's risk is about knowledge-transfer completeness, not model quality. LexAI's is about RAG citation grounding, not "the AI might make mistakes." RetailMind's is about fine-tuned-model drift against a moving catalogue, not "search might get worse." Each also names a concrete signal to monitor, which is what separates a real risk assessment from a disclaimer — a good answer tells you how you'd find out you were wrong before a customer, a partner, or a patient does.

**Overall quality signal:** For all three scenarios, the two-sentence answer to "why not just use the frontier model everyone's talking about?" is available directly from the memo: HealthBridge — because the data can't leave our private cloud, and a fine-tuned mid-tier model reaches the quality bar for this narrow task anyway; LexAI — because our IT team can't operate anything self-hosted and the volume doesn't justify frontier pricing on the highest-volume sub-task, though we do use frontier quality where the stakes justify it; RetailMind — because we do use frontier quality for the capability that needs it, and route the other 90% of volume to a fine-tuned model that costs a fraction as much for a task that doesn't need frontier reasoning. If your own memo can't produce an answer this specific in two sentences, the recommendation needs another pass before it's defensible.
