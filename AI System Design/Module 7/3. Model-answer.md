## Scenario A — HealthBridge: Clinical Documentation AI at Scale

**Recap of the scenario facts used below:** 500 physicians, 2 hospitals in pilot → 8 hospitals + 40 clinics at full scale. 2,000 encounters/day (pilot) → 10,000/day within 12 months → 15,000/day peak (flu season). Self-hosted, HIPAA-bound (data cannot leave the private cloud). Infra team has run the pilot on one GPU instance, with no autoscaling experience and no AI-incident runbook. The system generates SOAP-format note drafts from encounter transcripts (fed by an existing Azure Cognitive Services speech-to-text pipeline) for physician review before writing to Epic via FHIR.

### Section 1 — Scaling Strategy

**Autoscaling design:**

The workload is a single AI capability — one-shot SOAP note generation from an encounter transcript — running self-hosted for HIPAA reasons. Because it's self-hosted, GPU memory is the binding capacity constraint (Lesson 1), and the actionable *scale-out trigger* is **queue depth and P95 time-in-queue**, not GPU memory itself. GPU memory tells you how many concurrent generation slots a single node can hold; queue depth and time-in-queue tell you when the current fleet is falling behind demand and needs another node.

Assumptions: average encounter transcript is ~4,000 tokens (15–45 minutes of speech-to-text output), plus a ~2,000-token system prompt and SOAP-format few-shot block, for ~6,000 input tokens; output is a ~700-token draft note. Running a mid-tier open-weight model, 8-bit quantized, tensor-parallel across a 2-GPU node, each node holds 4 concurrent generation slots at this context length, with average end-to-end latency (queue + inference) of ~25 seconds per note.

At the 15,000/day flu-season peak, assume 70% of volume falls inside a 6-hour peak window across the network's shifts: 10,500 encounters ÷ 6 hours ≈ 1,750/hour ≈ 0.49/second. By Little's Law, concurrency = throughput × latency ≈ 0.49 × 25s ≈ 12.2 slots on average during the peak window; provisioning for P95 burstiness at roughly 2.5× average gives ~30 concurrent slots, or **8 nodes** at sustained flu-season peak.

- **Scale-out threshold:** P95 time-in-queue > 20 seconds sustained for 2 minutes, OR queue depth > (running nodes × 4 slots × 1.5) → add one node.
- **Scale-in threshold:** P95 time-in-queue < 5 seconds AND queue depth < (running nodes × 4 × 0.3), sustained for 10 minutes → remove one node, never below the minimum.
- **Minimum warm nodes:** 2, always running. Cold start on this class of self-hosted node (model load + warm-up) takes several minutes — pre-warming is required for a latency-sensitive, in-clinic workflow; a physician mid-encounter cannot wait for a cold start.
- **Maximum instance count:** 12 (8 needed at modeled flu-season peak + headroom for rolling deploys and a single hospital's local surge).

**Stateless vs. stateful considerations:**

Note generation is **stateless**: one transcript in, one SOAP draft out, no multi-turn accumulation. This is the easy case from Lesson 1 — trivially horizontally scalable behind a load balancer, no session pinning, no externalized session store needed for the AI tier itself. (Encounter-to-physician correlation — which patient, which physician, which room — is application state that already lives in the scheduling system, not AI-tier state.) This is a genuine architectural advantage relative to LexAI's and RetailMind's conversational features below.

**Caching architecture:**

| Cache layer | What is cached | Cache key | TTL | Target hit rate |
|---|---|---|---|---|
| Prefix/KV cache (vLLM shared-prefix caching) | The stable system prompt + SOAP-format instructions + few-shot example block (~2,000 tokens) shared by every call | Hash of the active prompt version | Until prompt version changes | ~100% of requests (every call shares this prefix) |
| Exact-match dedup cache | The generated note, keyed to protect against duplicate submission (client retry after a network timeout re-sends the same transcript) | Hash of the transcript + encounter ID | 24 hours | 2–3% (small, but avoids paying for redundant GPU compute on retries) |

Deliberately **not** using a semantic cache here: two encounters are never clinically interchangeable, even when superficially similar in phrasing. A semantically "close" cached note returned for a different patient's encounter would be a patient-safety failure, not just a quality miss — this is a caching decision driven by the domain, not a caching layer that was simply skipped.

**Peak load plan:**

Before flu season (which the infra team can anticipate — this is a known seasonal pattern, not a surprise event), load-test at 2× the modeled flu peak (≈30,000 encounters/day equivalent, ~60 concurrent slots / 15 nodes) using replayed de-identified transcripts, per production-readiness item 4. Because this is self-hosted, GPU capacity has real procurement lead time in a HIPAA-compliant private cloud — unlike elastic public-cloud autoscaling, the 12-node ceiling should be *reserved* ahead of the flu-season window (roughly November–February), not assumed available on demand.

Circuit breaker: if P95 time-in-queue exceeds 90 seconds even at the 12-node ceiling, the system degrades in two stages. First, new requests are queued with a "draft arriving shortly" notice rather than failing. If time-in-queue exceeds 5 minutes, the physician is prompted to document the encounter manually — the exact pre-AI workflow that already exists today. The AI component must never be the reason a clinical note doesn't get written; the fallback is the workflow HealthBridge already had before the pilot.

### Section 2 — Cost Architecture

**Assumptions:**

Self-hosted 2-GPU node in a HIPAA-compliant private cloud, reserved rate of **$9.50/hour**. Average tokens per encounter: 6,000 input + 700 output = 6,700 total. "Launch scale" here is the full-network rollout target (10,000 encounters/day); "peak" is the flu-season surge (15,000/day).

**Cost model at launch scale (10,000 encounters/day, 300,000/month):**

| Feature | Daily calls | Monthly tokens (in/out) | Monthly cost |
|---|---|---|---|
| Clinical note drafting | 10,000 | 1.8B in / 0.21B out (2.01B total) | ~$23,940 |
| **Total** | **10,000** | **2.01B** | **~$23,940** |

Because this is self-hosted, monthly cost is **not** token-volume × per-token price — it's node-hours × the reserved hourly rate. At steady 10,000/day full-network scale, the autoscaling range cycles between the 2-node minimum overnight and roughly 4 nodes during the day; modeling an average of 3.5 nodes running continuously: 3.5 × 24 × 30 = 2,520 node-hours × $9.50 = **$23,940/month**. Restating this as an effective blended rate ($23,940 ÷ 2,010 million tokens ≈ **$11.91 per million tokens**) is useful for comparing against the API alternative that HIPAA data-residency rules out — this is the accepted-risk tradeoff from the Module 3 build/buy framework, made concrete.

**Cost model at peak (15,000/day flu season, 450,000/month):**

Monthly tokens: 450,000 × 6,700 = 3.015B. During the flu-season window the fleet runs closer to its 8-node peak sizing, cycling down to a 4-node overnight minimum; modeling an average of 7.5 nodes: 7.5 × 24 × 30 = 5,400 node-hours × $9.50 = **$51,300/month** during flu-season months.

Blended annually: 9 non-flu months at $23,940 + 3 flu-season months at $51,300 = $215,460 + $153,900 = **$369,360/year**, or ~$30,780/month averaged — the figure to put in front of finance, since neither the launch-scale nor the peak figure alone represents the year.

**Cost optimization levers:**

| Lever | What it changes | Estimated monthly saving | Implementation effort |
|---|---|---|---|
| 4-bit quantization (from 8-bit) | More concurrent slots per node (4 → ~6), fewer nodes needed for the same peak throughput (~30% fewer nodes) | ~$7,000–$10,000 at steady state; proportionally more at flu-season peak | Medium — requires re-running the Module 6 golden-dataset evaluation before rollout; quantization changes model behavior and cannot be assumed quality-neutral |
| Prefix/KV caching of the stable system prompt | Avoids recomputing the ~2,000-token stable prefix on every one of 300,000+ monthly calls, improving effective node throughput | ~$2,500–$3,500 at steady state (≈10–15% fewer nodes needed for the same latency SLA) | Low — native vLLM feature, no new infrastructure |
| Pre-reserved flu-season capacity vs. emergency on-demand procurement | Avoids the premium of scrambling for GPU capacity in November when flu-season demand is already known months in advance | Not a per-token saving; avoids a capacity-cost spike and the risk of missing the ceiling entirely | Low — ops/procurement planning only |

### Section 3 — LLMOps Model

**Prompt versioning:**

The system prompt, SOAP-format instructions, and few-shot examples are stored in the same version-control repository as the orchestration code, per Lesson 3. Every version carries a semantic version identifier (e.g., v2.3.0), the author, the linked golden-dataset regression-run ID and result, and — because this content becomes part of a legal medical record — a **required sign-off field from a clinical informatics reviewer**, not just an engineer's approval. A version only moves from "draft" to "production-eligible" after the regression suite, the comparison evaluation, and the clinical sign-off all pass.

**Deployment process:**

1. Engineer proposes a prompt change as a pull request (no direct edits to the runtime configuration).
2. Automated regression suite runs against a fixed golden dataset (SOAP section completeness, structural validity, terminology checks) — must pass 100%, blocking on failure.
3. Comparison evaluation runs the new version against the current production version on a sample of recent de-identified transcripts, scored for groundedness against the source transcript and hallucination rate.
4. A clinical informatics reviewer manually reviews a sample of the comparison outputs — mandatory, not optional, given that this is a legal clinical document.
5. On all-clear, the version is promoted to production-eligible and rolled out to 5% of traffic (one hospital or clinic) for 48 hours, monitored in real time against the metrics below.
6. If stable, ramp to 25%, then 100% over the following week.
7. Any threshold breach at any stage triggers automatic rollback — a configuration change, not a redeploy.

Total time from proposal to 100% traffic: **roughly 1–2 weeks**, slower than a typical consumer LLMOps cadence — appropriately, given the clinical-review requirement.

**Evaluation gate:**

- 100% pass rate on the fixed regression suite (structure, section completeness).
- Groundedness score ≥ **0.97** against the source transcript (a very high bar, reflecting that fabricated clinical detail is not an acceptable failure mode at any rate).
- Hallucination/fabricated-detail rate on the comparison sample: **zero tolerance for any increase** over the current production baseline.
- Physician-edit-distance (how much a physician has to change the draft before signing) must not regress by more than **5%** versus the current production version.
- Clinical reviewer sign-off — a mandatory human gate alongside the automated thresholds, not a formality.

**Rollback trigger:**

Automatic rollback fires if, during staged rollout, format-compliance drops below **98%**, or the physician rejection rate (drafts discarded and rewritten from scratch rather than edited) rises more than **3 percentage points** above the current-version baseline within a rolling 4-hour window on the canary slice. The active prompt version is a runtime feature-flag value; reverting takes effect within one polling interval (target: under 2 minutes) with no code deployment, directly satisfying production-readiness item 19.

## Scenario B — LexAI: Legal AI at Full Firm Scale

**Recap of the scenario facts used below:** Meridian & Partners, 40 attorneys (pilot) → 200 attorneys across 3 offices. Research queries 10,000/month → 50,000/month; drafting tasks 1,000/month → 5,000/month. Pilot ran self-hosted on a single instance, no autoscaling, no prompt versioning, prompts edited directly in production configuration. A pilot attorney's direct prompt edit broke the citation format for three days before anyone noticed. Client confidentiality is paramount — one client's information must never surface to an attorney on a different matter. iManage (documents), Aderant (billing/matter IDs), Azure AD with matter-level access control.

### Section 1 — Scaling Strategy

**Autoscaling design:**

Two workloads with different profiles: **research queries** (RAG over iManage case files, moderate context, often multi-turn as an attorney refines a question) and **drafting tasks** (longer single-shot generation of a contract, motion, or correspondence draft off matter context). Both run on the same self-hosted infrastructure, mandated by the no-third-party-data-transit constraint rather than by raw scale — LexAI's traffic volume is modest.

Assumptions: research query ≈ 3,850 input tokens (3,000 retrieved chunks + 800 instructions + 50 query) / 500 output tokens; drafting task ≈ 4,000 input / 1,800 output tokens. Self-hosted single-GPU node (context sizes here don't require the 2-GPU tensor parallelism HealthBridge needs), $5.50/hour reserved.

At 200-attorney full scale: 50,000 research queries/month and 5,000 drafting tasks/month, concentrated across ~220 business hours/month (3 offices, overlapping hours), with a peak-hour concentration factor of ~3× average for both. Research peak ≈ 0.19 requests/sec at a ~10-second acceptable latency → concurrency ≈ 1.9 slots. Drafting peak ≈ 0.019 requests/sec at a ~25-second acceptable latency → concurrency ≈ 0.47 slots. Combined peak concurrency is small — **2–3 slots** — a genuine contrast with HealthBridge's much larger footprint: right-sizing to actual scenario scale matters more than copying an autoscaling group size across scenarios.

- **Scale-out threshold, tracked per request-class (research vs. drafting) separately**, since they have different latency SLAs and token profiles: P95 time-in-queue > 8s (research) or > 20s (drafting), sustained 2 minutes → add a node.
- **Scale-in threshold:** P95 time-in-queue under half the scale-out threshold for 15 minutes → remove a node, never below minimum.
- **Minimum warm nodes:** 1 (interactive latency for research queries requires it).
- **Maximum instance count:** 4 — covers redundancy across 3 offices plus deadline-driven bursts (e.g., simultaneous filings at multiple offices).

**Stateless vs. stateful considerations:**

Research queries carry **light conversational state** — an attorney refining "what about arbitration clauses specifically" after an initial answer. This state is externalized to Redis, keyed by session ID with a ~2-hour inactivity TTL, rather than pinned to an instance — with only 1–4 nodes total, sticky sessions would create uneven load and, on an instance failure, would drop an attorney's research context mid-session. Drafting tasks are **stateless**, one-shot generation off matter context.

**Caching architecture:**

| Cache layer | What is cached | Cache key | TTL | Target hit rate |
|---|---|---|---|---|
| Exact-match cache | Full response to repeated identical research queries (attorneys on the same matter often ask overlapping questions) | Hash of query text **+ matter/access-scope ID** (never just the query text — two attorneys with different matter access must never share a cache entry) | 24 hours (case-law references should stay current; a stale citation is a real professional-liability risk) | 8–12% |
| Prefix/KV cache | The stable system prompt and citation-format instructions shared by every call — the exact content that broke during the pilot incident | Hash of the active prompt version | Until prompt version changes | ~100% |
| Semantic cache (limited) | Paraphrased research queries — **scoped within a single matter's own query history only**, never global | Matter ID + semantic similarity within that matter | 24 hours | Small, single-digit % — deliberately not used as a primary lever |

Global semantic caching is explicitly ruled out: a semantic match across two different matters risks surfacing contextually similar but confidentially distinct information, which is the one failure mode this system cannot tolerate at any rate.

**Peak load plan:**

The "peak" in this scenario isn't a traffic-spike event like Black Friday — it's the sustained step-change from 40 to 200 attorneys, plus organic bursts around litigation deadlines. Before rollout: load-test the retrieval + generation pipeline at 5× the pilot's per-attorney query rate to confirm headroom for 200 attorneys, and — critically — re-run the exact failure conditions from the citation-format incident's postmortem as a go-live regression gate, so this specific incident cannot recur silently.

Circuit breaker: if the automated citation-format-compliance check fails on more than 2% of a rolling 100-response window, the system trips a **per-feature kill switch** that disables the research/drafting features for new queries and falls back to a "use Westlaw / manual research for now" message — disabling only the AI feature, not the firm's ability to work.

### Section 2 — Cost Architecture

**Assumptions:**

Self-hosted single-GPU node, $5.50/hour reserved. Research query: 3,850 in / 500 out tokens. Drafting task: 4,000 in / 1,800 out tokens. "Launch scale" is the full 200-attorney rollout.

**Cost model at launch scale (200 attorneys, 50,000 research queries + 5,000 drafting tasks/month):**

| Feature | Daily calls | Monthly tokens (in/out) | Monthly cost |
|---|---|---|---|
| Research queries | ~1,650/day | 167.75M in / 21.75M out (189.5M total) | — |
| Drafting tasks | ~165/day | 20M in / 9M out (29M total) | — |
| **Total** | **~1,815/day** | **246.5M** | **~$5,940** |

As with HealthBridge, self-hosted cost is node-hours × rate, not tokens × price. At full 200-attorney scale, the small computed concurrency (~2–3 slots) means the fleet mostly runs at its 1-node minimum, occasionally 2 during business hours: modeling an average of 1.5 nodes running continuously: 1.5 × 24 × 30 = 1,080 node-hours × $5.50 = **$5,940/month**. Effective blended rate: $5,940 ÷ 246.5M tokens ≈ **$24.10 per million tokens** — notably *higher* per token than HealthBridge, because a low-utilization self-hosted node still costs its full reserved rate regardless of how saturated it is. This is close to (arguably past) the crossover point where a comparable API-tier model might be cheaper per token — except self-hosting here is mandated by the no-third-party-transit confidentiality constraint, not chosen for cost. That premium is the accepted risk from the Module 3 build/buy framework, paid deliberately.

**Cost model at peak:**

Unlike HealthBridge's flu season or RetailMind's Black Friday, LexAI has no comparable seasonal spike — the step-change to 200 attorneys *is* the peak, already modeled above. The residual peak is deadline-driven bursts (roughly 1 week/month with elevated filing activity), during which average node count rises to ~2.2 for that week versus the 1.5-node baseline the other three weeks: blended monthly average = (2.2×1 + 1.5×3) ÷ 4 ≈ 1.68 nodes → 1.68 × 24 × 30 = 1,206 node-hours × $5.50 ≈ **$6,633/month** in a month containing deadline bursts — about a 12% increase over the baseline month, not a multi-fold spike.

**Cost optimization levers:**

| Lever | What it changes | Estimated monthly saving | Implementation effort |
|---|---|---|---|
| Route simple factual lookups to a smaller quantized variant on the same private infrastructure (not a public API, to preserve the no-third-party-transit constraint) | Reduces average per-query compute, letting the existing node handle more concurrent load before a second node is triggered | ~$1,000–$1,500 (modest in dollar terms at this scale; the larger benefit is deferring the cost of a second node) | Medium — needs an intent classifier plus evaluation that routing doesn't degrade legal-research quality |
| Reduce retrieved chunks passed to generation (top-k 8 → 4, with reranking, per Module 2) | Cuts average input tokens ~25% | ~$800–$1,200 plus avoided burst-node cost | Low–medium — reranking already assumed in the Module 2 retrieval design |
| Expand exact-match cache to cover common firm-wide (non-matter-confidential) procedural reference queries | Hit rate ~10% → ~15% via a curated, longer-TTL cache for genuinely firm-wide content | ~$300–$600 | Low |

At LexAI's scale, absolute dollar savings are small compared to HealthBridge or RetailMind — the point of these levers is node-count headroom before an unplanned capacity expansion, not a large line-item reduction.

### Section 3 — LLMOps Model

**Prompt versioning:**

This is the most consequential design element for LexAI given the pilot incident. Prompts move **out of the production configuration** (the exact anti-pattern that caused the three-day citation-format break) and **into version control** alongside application code, per Lesson 3. No individual attorney or engineer retains direct write access to the runtime prompt configuration going forward — that permission is what caused the incident, and it is revoked, not merely discouraged. Every version tracks: a semantic version ID, author, linked PR, the regression-suite result, the comparison-eval result, and a required **citation-format regression result** field that must show PASS — added specifically because of what happened. Approval requires sign-off from a senior attorney or the firm's AI governance lead, not an engineer alone, since assessing a citation-format or drafting-style change requires legal domain judgment.

**Deployment process:**

1. A change is proposed via pull request against the versioned prompt files — never a direct edit to the running configuration.
2. The regression suite runs against a fixed golden set of research/drafting cases, **including the specific citation-format check built from the incident's postmortem** — must pass 100%.
3. Comparison evaluation runs against a sample of recent, access-scope-appropriate queries.
4. A senior associate or partner on the AI governance committee reviews a sample of outputs for legal-drafting quality and citation accuracy.
5. On pass, staged rollout to 10% of traffic (one office) for 24 hours, with the citation-format-compliance metric monitored specifically in real time.
6. Ramp to 50%, then 100% over 3–4 business days if metrics hold.

Total time from proposal to 100%: **~1 week** — faster than HealthBridge's clinical process, since this domain's risk (professional liability) doesn't carry the same immediate patient-safety urgency, but still meaningfully slower than an unconstrained consumer rollout.

**Evaluation gate:**

- Citation-format compliance ≥ **99.5%** on the comparison sample — the single most important gate, targeting exactly the incident's failure mode.
- **Zero** cross-matter information leakage detected in access-control regression tests — binary, non-negotiable.
- Groundedness (faithfulness to retrieved source documents) ≥ **0.90** for research queries.
- Drafting-quality LLM-as-judge score no more than **2%** below the current production baseline.
- Mandatory human sign-off from the AI governance committee.

**Rollback trigger:**

Automatic rollback fires if citation-format compliance drops below **97%** on live canary traffic within any rolling 200-response window, or if **any** cross-matter leakage is detected — a single confirmed instance triggers immediate full rollback regardless of sample size. The rollback mechanism is the same feature-flag switch described above; because the production configuration is no longer directly editable by any individual attorney, this design closes the pilot's actual root cause, not just its symptom.

## Scenario C — RetailMind: E-Commerce AI at Peak Scale

**Recap of the scenario facts used below:** ShopSphere, 2M DAU baseline, live 3 months, Black Friday 10 weeks out, 5–8× normal traffic for 72 hours (known from the existing Elasticsearch infrastructure's history). AI components have only default autoscaling; the cost model has never been validated at peak; the system has never been load-tested at peak. Three AI capabilities: personalized discovery feed, conversational search (parses natural language into structured filters, does not replace Elasticsearch), and a multi-turn conversational shopping assistant. GDPR applies. Catalog changes must propagate within 5 minutes. The current rule-based engine drives 35% of purchases. A known governance gap (from Module 5): the shopping assistant occasionally states stale prices/availability from training data rather than live catalog data.

### Section 1 — Scaling Strategy

**Autoscaling design:**

Unlike HealthBridge and LexAI, RetailMind's AI layer is **API-based**, not self-hosted — there's no GDPR requirement to self-host, only to keep EU data in-region, which regional API endpoints or an EU deployment can satisfy. This changes what "autoscaling" means: there's no GPU node to add. Two different scaling problems exist side by side:

1. **Orchestration tier** (the ECS microservices coordinating requests): conventional request-rate/CPU-based autoscaling is fine here — this tier is doing routing and business logic, not inference.
2. **The AI-call layer itself**: the constrained resource is the **model provider's rate-limit/quota headroom** and the AI gateway's own concurrency management, not compute. The AI-specific signal that matters is still **queue depth and P95 time-in-queue** in front of the gateway — but the response to a growing queue is pre-negotiated higher provider quota and gateway-side load shedding, not "spin up another GPU node."

Assumptions: conversational search parses a query (~150 input tokens) into structured filters (~80 output tokens) and must complete within the existing **300ms P95 hard latency budget** (Module 2) — routed to a **small/fast-tier** model, since a frontier-tier reasoning call would blow this budget on both latency and cost. The shopping assistant handles multi-turn, higher-consideration conversations with tool calls to live price/availability (~1,200 input tokens including tool-call context, ~350 output tokens per turn), with a looser 2–4 second per-turn latency tolerance — routed to a **mid/frontier-tier** model.

Baseline volumes: ~700,000 search queries/day (2M DAU × 25% engagement × 1.4 queries/user), ~240,000 assistant turns/day (2M DAU × 3% engagement × ~4 turns/session). Black Friday, per the scenario's own 5–8× figure, applied at the conservative-for-capacity-planning upper bound of 8×: 5.6M search queries/day, 1.92M assistant turns/day, sustained for the 72-hour window.

Peak-hour concentration (assume 1.8× the daily average during the busiest hours): search ≈ 116.7 req/sec → concurrency ≈ 116.7 × 0.3s ≈ 35 slots average, ~70 with P99 headroom. Assistant ≈ 22.2 req/sec → concurrency ≈ 22.2 × 3s ≈ 67 slots average, ~134 with headroom.

- **Scale-out signal:** gateway queue depth or P95 time-in-queue crossing threshold (search: >500ms P95 sustained 30s; assistant: >6s P95 sustained 60s) → gateway increases its own concurrency ceiling up to the pre-negotiated provider quota, and orchestration-tier ECS scales conventionally alongside it.
- **Maximum instance count** (orchestration tier): sized to the modeled 8× peak plus headroom, using standard ECS scaling policy — not the focus of the AI-specific design.
- **Provider quota:** negotiated upward ahead of Black Friday specifically to cover the ~70 (search) + ~134 (assistant) peak concurrent-call figures — a capacity constraint self-hosted teams don't face, and the mirror image of HealthBridge's/LexAI's GPU-procurement lead time.

**Stateless vs. stateful considerations:**

Conversational search is mostly stateless per query, but the scenario's own follow-up refinement pattern ("make it blue") requires light session context — externalized to Redis, keyed by session ID, ~30-minute TTL. The shopping assistant is genuinely **stateful**: multi-turn conversation history and tool-call results (e.g., current cart contents) are externalized to Redis, never pinned to an instance — important at Black Friday scale, where orchestration instances churn heavily under autoscaling and a pinned session would be lost on instance replacement. The discovery feed is stateless at request time (it reads a precomputed personalization vector); the personalization computation itself is a batch pipeline fed by the CDP, not request-time AI-tier state.

**Caching architecture:**

This is the one scenario among the three where all three caching layers genuinely apply:

| Cache layer | What is cached | Cache key | TTL | Target hit rate |
|---|---|---|---|---|
| Exact-match cache | Full parsed-filter response for repeated search strings (deal-hunting drives many duplicate queries during Black Friday — "airfryer black friday deal," "50 inch tv under 300") | Normalized query text + applied filters | 15–30 min (short — price/availability/deals change fast during a sale event; a stale hit risks showing sold-out or mispriced items) | 30–40% |
| Semantic cache | Paraphrase variants of the same search intent ("cheap gift for a 7 year old who likes dinosaurs" vs. "affordable dinosaur toy for kid") | Query embedding similarity, threshold tuned conservatively toward precision | 15–30 min | 15–20% |
| Prefix/KV cache | Stable system-prompt/instructions for both the search parser and the shopping assistant | Hash of active prompt version | Until prompt version changes | ~100% |

Deliberately **not cached beyond a ~60-second TTL**: live price/availability tool-call results. Given the known governance gap (Module 5: the assistant has occasionally stated stale prices from training data), caching must never become a second source of stale pricing reaching a user — this row is short on purpose.

**Peak load plan:**

With 10 weeks of runway, load-test at 2× the modeled 8× peak (i.e., 16× baseline) at least 3–4 weeks before Black Friday, using synthetic traffic replayed from the existing Elasticsearch infrastructure's prior Black Friday logs — shaped into AI-feature query patterns, a real asset this team already has that HealthBridge and LexAI don't. Separately, and specifically because this is API-based: negotiate elevated rate-limit/quota ceilings with the model provider(s) ahead of the event — a peak-capacity constraint that has no equivalent in the self-hosted scenarios, where the equivalent constraint is physical GPU procurement instead.

Circuit breaker: if gateway queue depth or P95 time-in-queue exceeds threshold (search >500ms P95 sustained 30s, assistant >6s P95 sustained 60s) even after scaling, degrade in two ways. Conversational search falls back to **plain keyword-only Elasticsearch** — the pre-AI experience, which still fully works per the Module 4 integration requirement that "product search must still work." The shopping assistant pauses new session starts (existing sessions complete) and surfaces a "browse the catalog" fallback. The AI layer must never be the reason Black Friday search or checkout gets worse than it would be without AI — this protects the 35%-of-purchases baseline the rule-based engine already delivered.

### Section 2 — Cost Architecture

**Assumptions:** Illustrative tier pricing (not tied to any named model, per the model-landscape-snapshot convention): small/fast tier ≈ $0.30/M input tokens, $1.20/M output tokens; mid/frontier tier ≈ $4/M input tokens, $18/M output tokens; embedding ≈ $0.02/M tokens. Discovery feed: 2M DAU's personalization vectors refreshed 4×/day at ~500 tokens/refresh (registered-but-inactive users are not refreshed at this frequency).

**Cost model at launch scale (2M DAU baseline, 30-day month):**

| Feature | Daily calls | Monthly tokens (in/out) | Monthly cost |
|---|---|---|---|
| Conversational search (small/fast tier) | 700,000 | 3.15B in / 1.68B out | ~$2,961 |
| Shopping assistant (frontier tier) | 240,000 | 8.64B in / 2.52B out | ~$79,920 |
| Discovery feed (embedding refresh) | 2M users × 4 refreshes | 120,000M (120B) tokens | ~$2,400 |
| **Total** | — | — | **~$85,281** |

The shopping assistant dominates the bill — exactly what Lesson 2 predicts: LLM inference is the dominant, most usage-proportional cost line, and this is the one AI feature here routed to the expensive tier because its task genuinely needs it.

**Cost model at peak (Black Friday month: 3 days at 8× traffic, 27 days at baseline):**

Search: peak-day tokens = 5.6M queries × 230 tokens = 1,288M/day; 3 peak days + 27 baseline days (161M/day) = 3,864M + 4,347M = **8,211M tokens** this month (vs. 4,830M in a normal month — a ~1.7× monthly increase, not 8×). Cost ≈ in 5,353M×$0.30 + out 2,858M×$1.20 ≈ $1,606 + $3,430 = **~$5,036**.

Assistant: peak-day tokens = 1.92M turns × 1,550 tokens = 2,976M/day; 3 peak days + 27 baseline days (372M/day) = 8,928M + 10,044M = **18,972M tokens** this month (vs. 11,160M normal — again ~1.7×). Cost ≈ in 14,684M×$4 + out 4,288M×$18 ≈ $58,736 + $77,184 = **~$135,920**.

Embeddings: modest ~20% bump from higher Black Friday browsing activity: **~$2,880**.

**Total Black Friday month: ~$143,836** (vs. ~$85,281 baseline — a ~1.69× monthly increase).

This is the arithmetic that most teams get wrong in the anti-pattern direction: an 8× traffic event does **not** produce an 8× monthly bill, because the spike is only 72 hours inside a 30-day billing cycle — the naive mistake is announcing an 8× cost impact to finance. But the **instantaneous capacity** (concurrency, gateway rate limits, queue headroom) during those 72 hours must still be sized for the full 8×, regardless of how mild the averaged monthly cost impact looks. Capacity and cost are sized against two different denominators here, and conflating them in either direction is a mistake — understating the bill by assuming linear-with-DAU cost, or understating the infrastructure need by assuming the monthly-cost multiplier tells you how much capacity to provision.

**Cost optimization levers:**

| Lever | What it changes | Estimated monthly saving | Implementation effort |
|---|---|---|---|
| Further split assistant traffic: route simple confirmation turns (~40% of assistant volume, e.g., "is this in stock") to mid tier instead of frontier tier | Applies mid-tier pricing to a meaningful fraction of the dominant cost line | ~$15,000–$20,000 | Medium — needs an intent classifier and careful evaluation that quality doesn't regress on borderline "simple" queries |
| Exact-match + semantic caching on conversational search (already designed above) | Reduces both cost and, more importantly during Black Friday, **provider-quota consumption** | Modest in dollars (search is already the cheap tier) but frees real concurrency headroom during the 72-hour peak — the scarcer resource that week | Low–medium |
| Prompt/context compression for the shopping assistant (truncate tool-call payloads, compress conversation history after 4+ turns, per Lesson 2) | Cuts average input tokens on assistant sessions ~20% | ~$11,000–$14,000 | Medium |

### Section 3 — LLMOps Model

**Prompt versioning:**

System prompts for the search parser and the shopping assistant are stored in version control alongside application code, per Lesson 3. Each version tracks: version ID, author, linked regression/comparison-eval results, and — specifically because of the known price/availability governance gap — a required field confirming the tool-calling instruction for live price/availability lookups is present and unmodified (a change that silently weakened or removed the "always call the live-price tool" instruction is exactly the kind of regression this system needs to catch). Promotion to production requires the regression suite, comparison eval, and a product/governance reviewer sign-off.

**Deployment process:**

1. Engineer proposes a prompt change via PR.
2. Regression suite runs against a fixed golden set covering both features, including a specific check that the assistant still issues a live tool call for any price/availability claim rather than answering from parametric knowledge.
3. Comparison evaluation against a sample of recent production interactions, scored for factual accuracy on price/availability (checked against the live PIM/OMS data at eval time) and for search-filter-parsing precision/recall.
4. Staged rollout: 5% of traffic for a few hours (search's high volume means a meaningful sample accumulates fast), monitored for latency (300ms P95 for search) and factuality regressions.
5. Ramp to 25%, then 100% within 24–48 hours if metrics hold — notably faster than LexAI or HealthBridge, consistent with the lower per-error stakes of a single search result versus a clinical note or a legal citation.

**Evaluation gate:**

- Search-filter parsing precision/recall ≥ **95%** against the golden set, and P95 latency ≤ **300ms** in the comparison sample — a latency regression is a deploy-blocking failure here, not just a quality one.
- Assistant factual accuracy on price/availability claims: **100%** of claims must be backed by a live tool call in the regression suite (zero tolerance — this is the fix for the known governance gap).
- Assistant drafting/response quality (LLM-as-judge) no more than **3%** below baseline.
- Product/governance reviewer sign-off before 100% rollout.

**Rollback trigger:**

Automatic rollback if live-tool-call rate for price/availability claims drops below **99%** on canary traffic (a signal that the prompt regression has weakened the tool-calling instruction), or if search P95 latency exceeds 300ms for more than 2 minutes sustained on canary traffic, or if search filter-parsing precision drops more than 5 percentage points versus baseline. Rollback is a feature-flag revert, effective within one polling interval, no redeploy — and during the Black Friday window specifically, the rollback threshold windows are tightened (shorter sustained-breach requirement) given the higher cost of a slow detection during peak.

## Rubric Commentary

**AI-specific scaling metric:** All three answers reject CPU/memory autoscaling in favor of queue depth and time-in-queue, but the *reason* differs by architecture, and that distinction is the actual signal of understanding, not the metric names themselves. HealthBridge and LexAI are self-hosted — GPU memory bounds how many concurrent slots a node holds, but queue depth/time-in-queue is what tells you to add a *node*. RetailMind is API-based — there's no node to add; the same queue-depth/time-in-queue signal instead drives gateway concurrency management against a provider's rate-limit quota. A common mistake is to give the same generic answer ("scale on queue depth, not CPU") across all three without explaining what scaling *does* in each architecture — that's reciting the lesson, not applying it.

**Cost model arithmetic:** RetailMind's API-based token costing is the clean textbook case. HealthBridge and LexAI require converting self-hosted node-hours into an effective per-token rate — a step many answers skip, either applying the token-price formula naively to a self-hosted system (which has no per-token price) or leaving the self-hosted cost model as "just infrastructure cost" without connecting it back to the token volumes that drove the sizing. LexAI's low utilization (1.5 nodes for 246.5M tokens/month, ≈$24/M effective) versus HealthBridge's higher utilization (≈$12/M effective) is worth noticing directly — a good answer explains *why* the same self-hosting decision produces different unit economics depending on volume, not just that it does. RetailMind's peak-month arithmetic ($85K → $144K, a 1.7× increase from an 8× traffic event) is the second common failure point: an answer that reports an 8× cost increase has committed the exact linear-extrapolation anti-pattern this module names, just inverted — extrapolating a traffic multiplier onto a monthly bill instead of a user-count multiplier onto a monthly bill. Both are the same mistake.

**LLMOps evaluation gate:** Generic thresholds ("we'll run an eval and check it looks fine") don't score. Each scenario's gate should visibly target what's actually at risk in that scenario: HealthBridge's gate is anchored on clinical groundedness and physician-edit-distance because a fabricated clinical detail is a patient-safety event, not a quality miss. LexAI's gate is anchored on citation-format compliance specifically because that's what broke for three days in the pilot — an answer that designs a generic LLMOps pipeline for LexAI without a gate that would have caught *that specific incident* hasn't actually solved the presented problem. RetailMind's gate includes a hard latency threshold (300ms P95) alongside quality metrics, because for conversational search, slow is its own failure mode independent of correctness — a distinction the other two scenarios don't need to make as sharply.

**Production readiness honesty:** All three scenarios are written with an explicit tell: an inexperienced infra team (HealthBridge), a fresh, named incident (LexAI), and a system "never load-tested" with "only default autoscaling" (RetailMind). Each of these facts should mechanically produce several scores of 1 in the corresponding row — this model answer lands at 23/45, 22/45, and 24/45, each with 5–7 rows at a 1. A submission that scores its own design near-perfect either didn't read the scenario's stated gaps or is conflating "I described this component in my document" with "this component is operationally proven" — the rubric is checking for exactly that gap. Note also that a well-designed row in this document can still score low: HealthBridge's caching design is fully reasoned (score 2, not 1) precisely *because* it correctly excludes semantic caching for clinical safety reasons — good design and low operational-readiness are not contradictory, since design and proof-in-production are different things.

**Architecture diagram reflects production scale:** The test is whether the diagram could be redrawn from the *pilot* architecture description and still be accurate — if yes, it hasn't changed enough. HealthBridge's diagram must show an autoscaling node range and a manual-fallback path that the single-GPU pilot diagram wouldn't have. LexAI's diagram must show a prompt registry, staged-rollout controller, and feature-flag switch that are entirely new relative to "prompts edited directly in the production configuration." RetailMind's diagram must show the AI gateway's rate-limit-aware concurrency control and the circuit-breaker-to-keyword-search path — components a "defaults only" autoscaling setup wouldn't have. A common mistake across all three is submitting essentially the Module 2 (RAG) or Module 4 (integration) diagram unchanged, with a caching box added, without the LLMOps and observability layers this module specifically requires.

**Overall quality signal, applied across all three:** Could a new engineer, joining the week before flu season / full rollout / Black Friday, read this document and know what to do if the AI component degrades — without asking the author? Each scenario's Section 5 diagram and Section 4 gap list should function as that engineer's onboarding brief. If the diagram shows the fallback path and the gap list names a specific owner and timeline for each open item, the design is complete in the way this module asks for; if the fallback path only exists in prose in Section 1 and isn't in the diagram, or a "gap" is described without an owner, the design isn't finished yet.
