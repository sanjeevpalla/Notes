## 🎯 Session Overview

This class is the deep dive into why inference is expensive and the single most important idea behind fixing it: the **KV cache**. Starting from a recap of self-attention and causal masking, it walks through exactly why naive, uncached autoregressive decoding recomputes the same Key/Value projections over and over — a quadratic blow-up in total work — and why that recomputation is wasteful. From there it builds the full picture of modern inference engineering: the **prefill vs decode** split, the metrics that measure each (**TTFT**, **TPOT**), the **memory wall** that makes GPUs compute-rich but bandwidth-starved, the exact **KV cache memory formula** (worked by hand with real numbers), how KV caches are managed in production (eviction, VRAM budgeting, per-user scaling), and a live notebook demo proving the real-world speedup KV caching delivers. The class closes by opening the door to the first architecture built specifically to shrink the KV cache: **Multi-Query Attention (MQA)** — its mechanism, its trade-offs, and what its original paper's benchmark numbers actually show.

## 📚 Detailed Notes

### 1. Framing: From Naive Decoding to KV Cache

#### 📖 Recap — Why This Builds on Last Week

Everything in this class sits directly on top of self-attention and causal masking from the fine-tuning session: tokens → token IDs → embeddings → `softmax(QK^T / √d_k) V` → causal mask (upper/lower triangular, decoder-only, always **left padding**). The instructor is explicit that skipping this foundation makes KV cache meaningless: *"If you don't understand the transformers and its internals, then it really doesn't make sense to learn KV Cache."*

#### 🔍 The Core Problem: Naive Decoding Recomputes Everything

Autoregressive generation is inherently **sequential** — one token at a time, each depending on all previous tokens (the causal mask only allows looking at the past, never the future). Walking through a toy example ("the capital of France is Paris", tokenized as BOS/capital/of/France/EOS):

- At decode step 1, K and V are computed for all 4 input tokens.
- At decode step 2, the model must again compute K and V for those same 4 tokens **plus** the newly generated one — without caching, it recomputes all of them from scratch, even though tokens 1 through T-1 never changed.
- This repeats at every step: *"to generate one token, every time you are actually generating the K and the Vs"* — for the exact same prior tokens, again and again.

#### 🪜 The Quadratic Blow-Up

Total attention work across a full generation of N tokens, with no cache:

```text
Total work = 1 + 2 + 3 + ... + N = N(N+1)/2
```

Worked table (exact figures from class):

| Tokens Generated | Total K/V Calculations (no cache) |
|---|---|
| 8 | 36 |
| 32 | 528 |
| 128 | ~8,000+ |

> ⚠ This is **quadratic** growth in total recomputation work — the longer the generation, the more dramatically the waste compounds. This is distinct from (and should not be confused with) the KV cache's **memory** footprint, which — once caching is introduced — grows only **linearly** with sequence length (see Section 5).

#### 💡 Memory Trick

> *"Can't we store them?"* — the entire motivation for KV cache in one sentence. If tokens 1 through T−1 never change, save their K and V the first time they're computed, and only compute K/V for the newest token at each step.

#### 🎯 Key Takeaways

- Naive decoding = no memory of past K/V computations = the same work repeated at every single step.
- The growth is quadratic in total compute work without a cache.
- The fix (caching K and V) is conceptually simple — the rest of this guide is about exactly how that caching works and what it costs in memory.

### 2. Inference Performance Metrics: TTFT, TPOT, and the Prefill vs Decode Tradeoff

#### 📖 Definitions

| Metric | Definition | Tied To |
|---|---|---|
| **TTFT** (Time To First Token) | Time from submitting a prompt to receiving the first generated token | **Prefill phase** |
| **TPOT** (Time Per Output Token) | Time between consecutive generated tokens (T2−T1, T3−T2, …) | **Decode phase** |
| **TPS** (Tokens Per Second) | Related throughput metric, mentioned but not elaborated in depth | Decode phase |

> ⚠ The instructor initially mis-said "TOPT" and self-corrected live: *"Okay, it's TPOT, sorry, not TOPT."* TPOT is the canonical term.

#### 🔍 Prefill vs Decode — Why They Behave Differently

- **Prefill** processes the *entire prompt at once*, in parallel — every token's K, Q, V are computed simultaneously (or in large parallel chunks for very long prompts). This is what TTFT measures.
- **Decode** generates *one token at a time*, strictly sequentially, because of the autoregressive property. This is what TPOT measures, and it's the inherent bottleneck — typical rough estimate given: **~20–40 milliseconds per token** in modern LLMs (varies by model).

#### 🪜 Two Worked Scenarios

| Scenario | Prompt Length | Output Length | Which Phase Dominates | Result |
|---|---|---|---|---|
| A | 10,000 tokens | 20 tokens | **Prefill** | TTFT is high/expensive; decode is cheap |
| B | Small prompt | Large output (e.g. long-form generation) | **Decode** | TTFT is low; decode becomes the bottleneck since it must sequentially generate many tokens |

> 💡 **Newspaper analogy:** *"The pre-filled part is just like reading some newspapers. First you read the entire paper, and then if you want to inference, then you want to write a summarized report. That becomes your generative, or the decoding step."*

A student (Sridhar) asked about summarization specifically (10,000 tokens in, 300 out) — confirmed: TTFT will be higher here because more tokens must be processed into K/V before generation can even begin.

#### ⚠ Why Streaming Exists

TPOT can vary within a single generation (e.g., token 1 at 20-30ms, token 2 at 21ms), but the more operationally important number is **TTFT** — a slow TTFT could mean waiting several minutes with *zero* visible output. **Streaming** (returning each token as it's generated, rather than waiting for the full response) is the UX mitigation for this.

#### 🎯 Key Takeaways

- TTFT ≈ prefill cost; TPOT ≈ decode cost — know which one a given workload stresses.
- Long-prompt/short-output workloads stress prefill (TTFT); short-prompt/long-output workloads stress decode (TPOT × number of tokens).
- Streaming doesn't make generation faster — it makes the *wait* feel shorter by surfacing partial output immediately.

### 3. The Memory Wall: Compute Throughput, Memory Bandwidth, and Arithmetic Intensity

#### 📖 The Two Hardware Quantities

| Quantity | Unit | What It Measures |
|---|---|---|
| **Compute throughput** | TFLOPS (10¹² floating-point ops/sec) | How fast the GPU can *compute* |
| **Memory bandwidth** | GB/sec | How fast data can be *moved* into the GPU for computation |

> ⚠ Data is **not** sitting ready inside the GPU by default — *"At every point of time, you need to move the data."* This move (RAM → VRAM) has its own speed limit, independent of how fast the GPU can crunch numbers once the data arrives.

#### 🔍 Arithmetic Intensity

**Definition:** how much computation can be performed for every byte of data moved from memory.

| Case | Data Moved | Ops Performed | Verdict |
|---|---|---|---|
| 1 | 1 GB | 10 billion ops | **Low** arithmetic intensity |
| 2 | 1 GB (same) | 100 billion ops | **Higher** arithmetic intensity (better, though still below a 1,000-TFLOPS GPU's theoretical ceiling) |

> 🎯 **The goal is high arithmetic intensity**, not "balance." *"If you have less bandwidth, and if you have a GPU with high compute, it really doesn't make sense, because the processing speed automatically becomes lesser... there is a bottleneck."* Without data arriving, the GPU sits idle regardless of its theoretical compute ceiling.

#### 💡 Kitchen/Chef Analogy

> *"Chef can cook 100 dishes per second. But the kitchen can only deliver [ingredients for] 20 dishes."* The chef (compute) spends most of their time waiting on ingredients (memory bandwidth) — ending up serving only "20, 20, 20, 20, 5" per round instead of 100. **This is the memory wall problem** — compute capability vastly outstripping the rate at which data can be supplied to it.

#### ⚠ Hardware, Not Software, Is the Fix

Repeated explicitly in Q&A (student Ayush asked about software-level optimization of KV cache block placement for better memory parallelism): *"Use better hardware. Hardware is the solution here. Software can do nothing... You need good quality of hardware"* — citing specialized processors and DDR5 RAM as concrete examples; older RAM generations directly degrade this bottleneck.

#### 🎯 Key Takeaways

- Memory wall = GPUs can compute far faster than data can be delivered to them.
- Arithmetic intensity measures how well you're using the data you've already paid the bandwidth cost to move.
- This problem is fundamentally architectural/hardware-level — no amount of clever code eliminates the underlying bandwidth ceiling, though reducing *how much data you need to move* (smaller KV cache) helps relieve pressure on it.

### 4. VRAM Budgeting: Model Weights, KV Cache, and Headroom

#### 📖 VRAM Composition, in Order

1. **Model weights load first** — commonly **more than 40%** of VRAM, depending on overall load.
2. **KV cache sits on top**, because KV cache generation is only possible once the model itself is loaded: *"Without the model, is it possible to generate your K and V? It is not possible."*
3. **~5% headroom** reserved, because *"if some other process comes into account, the entire step will break."*

> ⚠ The instructor explicitly flags the 95%-utilization figure as a rough rule, not a hard law: *"this 95 number is also not exactly correct."*

#### 🔍 Context Window Clarified

> *"Context window is simply the max sequence length of any type of model."* (Answered directly in Q&A to student Arun.)

#### 🎯 Key Takeaways

- VRAM is allocated model-weights-first, KV-cache-second, with a small safety margin left over.
- The 95%/5% split is a practical heuristic, not an exact spec.
- Context window = max sequence length — a term worth distinguishing clearly from "max tokens to generate," which is a separate, often API-configurable parameter (see Section 7).

### 5. The KV Cache Memory Formula, Derived by Hand

#### 📖 The Formula

```text
KV cache (bytes) per token = 2 × num_KV_heads × head_dim × num_layers × dtype_bytes

Total KV cache memory = KV_per_token × sequence_length × batch_size
```

| Factor | Meaning |
|---|---|
| **2** | Two separate tensors — one for K, one for V |
| **num_KV_heads** | Number of KV heads (in standard MHA, equal to the total number of attention heads) |
| **head_dim** | Dimension per attention head |
| **num_layers** | Total transformer blocks in the model |
| **dtype_bytes** | Bytes per value for the chosen precision: FP16 = 2, FP32 = 4, FP64 = 8 |

#### 🪜 Step-by-Step Worked Example

Assumptions stated explicitly in class: 8 KV heads, head dimension 64, 32 layers, FP16 (2 bytes).

```text
1. K dimension total:     8 heads × 64 dim = 512
2. V dimension total:     8 heads × 64 dim = 512
3. K + V combined:        512 + 512 = 1024
4. × dtype bytes (FP16):  1024 × 2 = 2048 bytes = 2 KB   (per token, per layer)
5. × num_layers (32):     2 KB × 32 = 64 KB              (per token, whole model)
6. × sequence_length:     64 KB × N tokens
```

> ⚠ **Numeric note:** the instructor's live spoken aggregate totals for 10,000 and 100,000 tokens didn't fully reconcile with each other in the transcript. Using the clean per-token figure he derived (**64 KB/token**) and multiplying straight through:
> - 10,000 tokens → 64 KB × 10,000 = **~625 MB (~0.64 GB)**
> - 100,000 tokens → 64 KB × 100,000 = **~6.25 GB**
>
> Use this clean recomputation rather than any single spoken total — the formula and per-token figure are the reliable part; treat any specific spoken aggregate as approximate.

#### 🔍 Conclusion: Linear, Not Quadratic

> *"The KV cache is growing **linearly**"* with sequence length — once caching is in place, the *memory* cost per additional token is constant and additive. This is the crucial distinction from Section 1's quadratic **compute** blow-up: caching fixes the compute-redundancy problem, but the cache itself still grows (linearly) in memory as the sequence gets longer.

#### 📊 Realistic Model-Size Table (approximate, instructor's own figures, flagged as rough)

| Model | Layers | Heads | Head Dim | Approx. KV Cache |
|---|---|---|---|---|
| Llama-2 ~7B | 32 | 32 | 128 | Roughly a few GB, scaling with sequence length (instructor's own figures here were imprecise/garbled in the live session — treat only the formula as reliable, not this specific total) |
| ~70B-class model | — | — | — | Scales up further per the same formula — more layers/heads directly increase per-token cache size |

> ⚠ The instructor explicitly caveated these particular model-size figures as rough/approximate ("I've taken ish... rough estimated") — don't treat the specific GB numbers as precise; the formula itself is the reliable takeaway.

#### 🎯 Why Q Isn't in the Formula

Student Rahul asked directly: *"Why not Q, sir?"* Answer: *"You don't have to calculate any Q. This is the math for K and V cache"* — Q isn't reused across decode steps the way K and V are, so it's never cached.

#### ⚠ Training vs Inference — An Explicit Checkpoint Question

The instructor quizzed the class directly: *"Whatever the things that we have discussed today, is it from training perspective or inferencing perspective?"* Answer: **entirely inferencing**. *"During training, K and V are parallelly calculated, but nothing is saved. Only during inferencing, we need to save the KV."*

#### 🪜 Decoding the Formula From the End — What's Actually a Lever

| Formula Factor | Changeable? | How |
|---|---|---|
| `dtype_bytes` | ✅ Yes | Quantization — but explicitly framed as a **last resort**: *"quantization is not the first step that we do. We take it at the last."* |
| `num_layers` | ❌ No | Fixed by model architecture |
| `head_dim` | ❌ No (in base MHA) | Fixed by model architecture |
| **`num_KV_heads`** | ✅ **Yes — this is THE lever** | *"This is the part that we'll be playing with... that particular thing will be changing in the next algorithm"* — i.e., MQA (Section 11) |

### 🎯 Key Takeaways

- Memorize the formula: `2 × num_KV_heads × head_dim × num_layers × dtype_bytes`, then × sequence_length × batch_size.
- KV cache memory grows **linearly** with sequence length (distinct from the quadratic compute cost it eliminates).
- Of the formula's factors, **num_KV_heads is the only architecturally-flexible lever** without resorting to quantization — this is exactly what MQA (and later GQA) change.

### 6. What Actually Drives KV Cache Size: Dtype, Batch Size, Sequence Length

#### 🔍 Dtype Impact

Doubling bytes-per-value doubles cache size at that step of the formula:

| Precision | Bytes | Relative Size |
|---|---|---|
| FP16 | 2 | 1× (baseline — preferred for inference) |
| FP32 | 4 | 2× |
| FP64 | 8 | 4× |

> 🚀 **Best practice:** *"Most of the times we prefer working with [FP]16. [FP]32 is not a preferred choice"* for inference.

#### 🔍 Batch Size Impact

A single inference request uses a multiplier of 1; **10 parallel requests multiply the total KV cache by 10**, directly, as a straight multiplicative factor in the total-memory formula.

#### 🔍 Sequence Length Impact

Already covered in Section 5 — linear scaling, directly multiplying the per-token cache figure.

#### 🔍 Parameter Count → Cache Size Relationship

Student Devajoshi asked: *"Is the size of KV cache dependent on the parameter volume of a model?"* Answer: **Yes** — more parameters typically means more layers, and `num_layers` is a direct multiplicative factor in the formula.

#### 🎯 Key Takeaways

- Four independent multipliers compound the total KV cache size: dtype bytes, batch size, sequence length, and the architecture-fixed layer/head/dim factors.
- Precision choice (FP16 vs FP32) is a straightforward, immediate lever — but quantization generally comes last in the optimization order, not first.

### 7. KV Cache in Production: Lifecycle, Eviction, and Per-User Scaling

#### 📖 Defaults

KV caching is **enabled by default** in every modern inference stack (Hugging Face Transformers, VLLM). Disabling it requires an explicit manual flag: *"In Transformers, `use_cache` is equal to true. By default, it is always enabled."*

#### 🔍 Where the Cache Lives

The KV cache sits **only** on GPU/VRAM — never moved back to CPU. A student (Saravana) suggested storing it in system RAM instead; rejected explicitly: *"No, no, no, the idea is it has to be in GPU only. Then only it makes sense."*

#### 🪜 Eviction Policy — Driven by VRAM Budget, Not a Fixed Rule

| VRAM Availability | Eviction Behavior |
|---|---|
| Scarce | Clear cache after every request, or every few requests |
| Abundant | Hold cache longer — e.g. after 200, 500, or 1,000 requests |

**Rule of thumb cited:** if the model takes 20–30% of VRAM, reserve 60–70% for the KV cache. Concrete example given: on an **H100 80GB**, if the model takes ~20GB, allocate close to **~50GB for KV cache**.

> ⚠ Input sequence length matters independently of request count — a handful of very long prompts (1,000+ or even 15,000 tokens) can blow up memory regardless of how many requests you're serving.

#### 🔍 Per-User Scaling Reality Check

> *"If you are trying to serve 10,000 users, do you think that you can hold all the [KV] cache for every user in the GPU memory? Practically not possible."* Even large-VRAM setups (300–400GB across multiple containers) can only hold so much — *"not for 100 users... once it starts growing 1,000, 2,000, you need to free up your KV cache."* A new, unrelated prompt from a different user makes the old cache useless: *"every prompt has its own new KV cache."*

#### 🔍 TTL-Based Eviction?

Student Murtaza asked whether the cache clears after a fixed time-to-live (TTL). Answer: **not necessarily** — *"totally depends. If you have the memory, then you can use TTL. Otherwise, simply what you have to do, remove it for the next inference."*

#### 🔍 Can KV Cache Be Quantized?

Yes — confirmed directly to student Viraj: *"Yes, for sure, you can. You can apply quantization on top of KV cache also."*

#### 🎯 Key Takeaways

- Caching is on by default everywhere; turning it off is a deliberate, non-production action.
- Eviction is budget-driven (VRAM availability + request volume + prompt length), not a fixed timer by default.
- At real scale, holding every user's cache indefinitely is simply not feasible — caches must be freed as volume grows.

### 8. KV Cache Beyond Decoder-Only Models: Cross-Attention and Encoder-Decoder Architectures

#### 🔍 Does KV Caching Apply Outside Decoder-Only Models?

Yes, explicitly confirmed (Q&A with student Gaurav Garg): KV caching applies **anywhere** K and V are computed — *"because otherwise, the computation grows quadratically"* regardless of architecture family. This includes:

- The **original 2017 "Attention Is All You Need"** encoder-decoder architecture.
- **Cross-attention** in encoder-decoder (seq2seq) models like T5: *"the idea is that from the cross-attention, you transfer the K and V to the decoder... you need to save it in the cache."*
- Both the encoder's own self-attention and the decoder's own self-attention independently use the KV cache concept too: *"everywhere you are calculating KQV, there KV cache comes into the system."*

#### 📖 Historical Note: Cross-Attention Predates Self-Attention

Cross-attention appeared earlier than the Transformer's self-attention — in **2014 Bahdanau attention** (an additive attention mechanism), well before "Attention Is All You Need" (2017) introduced self-attention.

#### 🔍 Max Tokens vs Context Window

Clarified separately: the **max generation length** (max tokens to output) is often a configurable API/provider parameter, distinct from the model's **native context window**, which end users of commercial APIs typically cannot alter — they can only tune how many tokens they're allowed to generate within that fixed window.

#### 🎯 Key Takeaways

- KV caching is a general technique tied to "wherever K/V get computed," not a decoder-only-specific trick.
- Encoder-decoder models cache cross-attention K/V (from encoder to decoder) in addition to each side's own self-attention K/V.
- Max-tokens-to-generate ≠ context window — know the difference when discussing API-level configuration vs model architecture.

### 9. Caching Terminology: KV Cache vs Prompt Cache vs Prefix Cache vs App-Level Cache

#### 📊 Comparison Table

| Term | What It Is | Typical Lifetime | Example |
|---|---|---|---|
| **KV cache** | Per-request/session cache of computed K/V tensors in VRAM | Tied to the active session/request | Core inference-engine mechanism covered throughout this guide |
| **Prompt cache** | Provider-level cache of previously-seen prompt segments (surfaced e.g. as "cached prompt tokens" in OpenRouter) | Short — *"probably 5 minutes, 10 minutes"* | Anthropic's prompt caching (cited as the origin of this industry trend: *"Anthropic has a dedicated blog on prompt caching, because they started that. After that, everybody started."*) |
| **Prefix caching** | Caching shared prompt prefixes across multiple requests, tied conceptually to the prefill phase | Varies by implementation | Deferred in depth to the future **Paged Attention** topic |
| **Classical app-level cache (e.g. Redis)** | Ordinary software caching of prompt/response pairs for conversational memory | Application-defined | *"There is nothing AI-related to that... normal SDLC cache"* |

#### 🎯 Key Takeaways

- These four terms are easy to conflate but refer to genuinely different mechanisms, lifetimes, and layers of the stack.
- KV cache and prompt cache can be **provider-dependent** in which one actually gets reported/metered to you.
- Not every "cache" in an LLM application is AI-specific — classical software caching (Redis) still has its place for conversational memory, separate from any of the inference-level caches above.

### 10. Notebook Demo: Measuring the Real Speedup from KV Caching

#### 🪜 Setup

- Model: **SmolLM2** (~1.7 billion parameters, lightweight)
- Precision: FP16, on CUDA (**T4 GPU minimum recommended**)
- `model.eval()` for inference mode
- Example prompt: *"The red cat was..."*
- `max_new_tokens=300`, 3 runs per condition, `torch.cuda.synchronize()` around timing, `torch.no_grad()` context

#### 💻 Code Example (reconstructed from the instructor's live walkthrough)

```python
import time
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

device = "cuda"
model_name = "HuggingFaceTB/SmolLM2-1.7B"

tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.float16
).to(device)
model.eval()

prompt = "The red cat was"
inputs = tokenizer(prompt, return_tensors="pt").to(device)

def measure_generation_time(use_cache: bool, num_runs: int = 3, max_new_tokens: int = 300):
    times = []
    for _ in range(num_runs):
        torch.cuda.synchronize()
        start = time.perf_counter()
        with torch.no_grad():
            model.generate(**inputs, max_new_tokens=max_new_tokens, use_cache=use_cache)
        torch.cuda.synchronize()
        times.append(time.perf_counter() - start)
    return times

no_cache_times = measure_generation_time(use_cache=False)
with_cache_times = measure_generation_time(use_cache=True)
```

#### 📊 Results (exact figures reported in class)

| Condition | Avg. Generation Time (300 tokens) |
|---|---|
| `use_cache=False` (no KV cache) | **15.773 seconds** |
| `use_cache=True` (KV cache, the default) | **~8 seconds** |

| Metric | Value |
|---|---|
| Time saved | ~7 seconds |
| Reduction | **48.8%** |
| Speedup | **~1.9×** |

> ⚠ The instructor framed the expectation *before* revealing the result, as a comprehension check: *"Without the cache is coming close to 15.773 seconds. Now, the idea is, with cache, it should be higher, yes or no? ... it has to be lower."*

> 📌 Note: this demo measured **timing only** — no separate VRAM/memory-usage comparison (with vs without cache) was run live. The memory formula in Section 5 is a separate, hand-calculated exercise, not tied to a live memory-profiling run on this notebook.

#### 🎯 Key Takeaways

### 11. From MHA to MQA: Sharing Keys and Values Across Heads

#### 📖 MHA Recap (the Bridge Into MQA)

In standard Multi-Head Attention, **every head computes its own independent K, Q, and V**. With H heads, there are H separate (K, Q, V) triples — e.g., 8 heads → 8×3 = 24 total matrices. After per-head attention, outputs are concatenated (and then passed through a feed-forward layer). This is expensive during inference specifically because the KV cache must store K and V **for every head separately, for every previous token**.

#### 🔍 The MQA Idea

**Keep the number of attention heads the same.** Make **all heads share a single, unified K and V** (one K/V pair total, instead of one per head). Only the **projection dimension** of K and V changes — not the number of heads, and not Q.

#### 💻 Worked Dimension Example

```text
Standard MHA:
  embedding_dim = 512, heads = 8, head_dim = 64
  Q: 8 × 64 = 512    K: 8 × 64 = 512    V: 8 × 64 = 512

MQA:
  Q: 8 × 64 = 512   (UNCHANGED — Q keeps full per-head dimensionality)
  K: single shared 64-dim vector     (was 512, now just 64 — ONE copy, not eight)
  V: single shared 64-dim vector     (was 512, now just 64 — ONE copy, not eight)
```

> ⚠ The reduced dimension (64 in this example) is illustrative, not a strict rule: *"It's not necessary... the idea is, it has to be of lower dimension"* than the embedding dimension.

#### 🪜 The Mechanism, Precisely

- K and V are generated **once per token** (not once per head), then **shared/read** by all query heads — they are not independently or redundantly recomputed by each head.
- Only Q is generated independently per head, each capturing its own nuances.
- Every query head (Q1...Q8) reads the *same* shared 64-dim K and 64-dim V.
- The attention formula itself is unchanged: `softmax(QK^T / √d_k) V` — only what feeds into K and V differs.

> 💡 **Important clarification (raised live in Q&A, not originally planned):** this resolves a natural confusion about 8 heads "updating" one shared memory independently — there's no race condition, because only **one** computation produces K/V per token, and all heads simply read from it.

#### ⚠ Why Sharing K/V Doesn't Mean Identical Attention Outputs

> *"Never think about like K and V will actually produce the same attention pattern... Every head will never produce the same attention [pattern]. It will always be different."* Because **Q still differs per head**, the attention scores (`QK^T`) still differ per head even against the same shared K — only the K/V inputs are shared, not the resulting attention computation.

#### 🚀 Benefits

1. **KV cache shrinks dramatically** — example cited: going from 32 separate per-head K/V sets down to 1 shared pair yields **"32 times less KV cache."**
2. **More compute capacity freed during decode** — directly ties back to the memory wall: a smaller cache means less data that must move from RAM to VRAM, improving effective bandwidth utilization.
3. Faster generation overall, due to reduced redundant computation and smaller cache-transfer overhead.

#### ❌ The Cost: "Attention Diversity"

With many independent K/V sets (MHA), the model captures a **wider diversity** of attention patterns across the data. With one shared K/V (MQA), that diversity **drops** — this is the central trade-off.

> ⚠ A student (Paritosh) suggested "hallucination" as the term for this cost — explicitly rejected: *"No, no, no, hallucination is not the correct term."* "Attention diversity" is the instructor's own descriptive term for this trade-off, not standardized literature terminology.

#### 🪜 Dimension Bookkeeping Rule (repeated because it's a common point of confusion)

> *"You change the projection and not the head."* The **number of heads never changes** in MQA. What changes is purely the **output dimension of the K and V linear projections** (the W_K, W_V weight matrices are reshaped into a smaller output space), shared across all heads — while Q retains its full per-head dimensionality. Q's dimension cannot be reduced below what the model's embedding dimension requires — it *can* be increased, never decreased.

#### ⚠ A Critical Deployment Constraint

Confirmed directly to student Arun Subramanian: **you cannot retroactively convert an MHA-trained model to MQA at inference time.** If you want MQA's inference benefits, **you must train the model with the MQA architecture from the start** — *"you cannot change that... you cannot use MQA"* post-hoc on a model trained as MHA.

### 🎯 Key Takeaways

- MQA: same number of heads, shared single K/V pair across all of them; only K/V projection dimension shrinks, never Q.
- The trade-off is reduced "attention diversity," not hallucination — a distinct and important terminology point.
- MQA is an architectural choice baked in at training time — it is not an inference-time trick you can retrofit onto an already-trained MHA model.

### 12. The MQA Paper: BLEU Scores, Beam Search, and the Real Win

#### 📖 The Paper

**"Fast Transformer Decoding: One Write-Head Is All You Need"** (Noam Shazeer, 2019, arXiv — not published at a formal peer-reviewed conference). The title plays on "Attention Is All You Need."

#### 📊 BLEU Score Results (exact figures read from the paper in class)

| Configuration | BLEU Score |
|---|---|
| Multi-Head Attention (MHA), default config (8 heads, dim 128, 4096) | **26.7** |
| Multi-Query Attention (MQA), same default config | **26.5** |
| MQA with beam search (beam = 4), one encoder-decoder configuration | **28.5** |
| (Additional reference figure, billion-word LM benchmark) | **~32.2** |

**Conclusion drawn in class:** *"There is not real improvement if you're bringing multi-query attention"* on raw output quality — in fact a very slight regression (26.7 → 26.5) at default settings. With beam search variations, results shift around but aren't universally better for MQA either: *"not every time"* does beam search help.

#### 🔍 Beam Search Tangent (Deferred Detail)

Two broad decoding-technique families were distinguished:

- **Deterministic** — beam search: explores a decision tree of multiple candidate future token sequences rather than committing to a single next token.
- **Stochastic** — top-k / top-p sampling.

> ⚠ Beam search is explicitly flagged as **largely obsolete** for modern LLMs: *"Beam search is not relevant now. Newer LLMs, they don't use beam search"* — it was historically heavy in machine translation and classical NLP since roughly 2000.

#### 🎯 The Real Verdict

> *"MQA is [not] really a game-changer"* from a pure model-quality standpoint — MHA and MQA perform **very, very close** on benchmark scores. The actual game-changing benefit is specifically from the **KV cache / inference-efficiency perspective**.

Direct confirmation via a class question — *"who will be generating faster? Multi-head attention or multi-query attention?"* — Answer: **MQA generates faster**, due to reduced cache size and computation, even though raw quality metrics are nearly identical to MHA.

#### 📖 Historical Positioning

- MQA paper: 2019.
- GQA (the "middle ground" between MHA and MQA, covered next class): roughly 2023.
- Instructor's own stated current alignment: *"I'll be lesser aligned towards MQA and much more aligned towards GQA... because GQA is a middle ground between MHA and MQA."*

### 🎯 Key Takeaways

- MQA's BLEU scores are nearly identical to MHA's (26.5 vs 26.7 default) — the architecture is not a quality upgrade.
- MQA's actual value proposition is entirely about **inference efficiency** (smaller KV cache, faster generation), not raw output quality.
- Beam search, while relevant to how the paper reports some of its numbers, is itself a largely obsolete technique in modern LLM deployment.

## 📝 Glossary

| Term | Definition | Why It Matters |
|---|---|---|
| KV Cache | Stored Key/Value tensors from previous tokens, reused instead of recomputed at each decode step | Eliminates the quadratic recomputation cost of naive decoding |
| TTFT | Time To First Token — latency dominated by the prefill phase | Key UX metric for how long a user waits before seeing any output |
| TPOT | Time Per Output Token — latency per token during the decode phase | Key metric for sustained generation speed |
| Prefill | Parallel computation of K/V for the entire input prompt at once | Happens before any token is generated; determines TTFT |
| Decode | Sequential, one-token-at-a-time generation | Bottlenecked by the autoregressive property; determines TPOT |
| Memory Wall | The mismatch between GPU compute throughput and memory bandwidth | Explains why reducing data movement (not just adding compute) speeds up inference |
| Arithmetic Intensity | Computation performed per byte of data moved from memory | Higher is better — measures how well compute capacity is actually utilized |
| Quantization | Reducing the bytes-per-value used to store weights/cache (e.g. FP32→FP16→INT8) | A lever for shrinking KV cache size, but treated as a last resort, not a first step |
| Cross-Attention | Attention where K/V come from the encoder and Q comes from the decoder | Also benefits from KV caching, in encoder-decoder (seq2seq) architectures |
| Prompt Cache | Provider-level cache of previously-seen prompt segments | Distinct from KV cache; shorter-lived; the origin of the "prompt caching" industry trend traces to Anthropic |
| Multi-Query Attention (MQA) | Attention variant where all heads share one K/V pair, reducing KV cache size | The first KV-cache-reduction architecture covered in this series |
| Attention Diversity | Instructor's term for the variety of attention patterns captured across heads | The trade-off MQA makes in exchange for a smaller KV cache |
| Beam Search | Deterministic decoding technique exploring multiple candidate sequences | Largely obsolete in modern LLM deployment; still referenced in older benchmark papers like MQA's |

## 🔄 Revision Notes — One-Minute Revision

- Naive decoding recomputes K/V for every prior token at every step — quadratic total compute work (N(N+1)/2).
- KV cache fixes this by storing K/V once computed — memory then grows linearly, not quadratically.
- TTFT ≈ prefill cost (parallel, whole-prompt); TPOT ≈ decode cost (sequential, one token at a time).
- Memory wall: GPUs compute faster than data can be delivered — arithmetic intensity measures how well you use data once it arrives; the fix is fundamentally hardware, not software.
- KV cache formula: `2 × num_KV_heads × head_dim × num_layers × dtype_bytes`, then × sequence_length × batch_size.
- Of the formula's factors, only `num_KV_heads` (and, as a last resort, `dtype_bytes` via quantization) are real reduction levers — this is exactly what MQA targets.
- KV cache lives only in VRAM, is on by default everywhere, and is evicted based on VRAM budget + request volume, not necessarily a fixed TTL.
- KV caching applies beyond decoder-only models — cross-attention in encoder-decoder architectures caches K/V too.
- MQA: same number of heads, one shared K/V pair; BLEU scores nearly identical to MHA (26.5 vs 26.7); the real win is inference speed, not quality — and it must be trained in from the start, not retrofitted.
- GQA, MLA, RoPE, and Paged Attention are all deferred to the next class(es).

## 📋 Cheat Sheet

```text
QUADRATIC COMPUTE (no cache):  Total work = N(N+1)/2
LINEAR MEMORY (with cache):    KV memory grows linearly with sequence length

TTFT  → prefill phase  → parallel, whole-prompt
TPOT  → decode phase   → sequential, one token at a time

KV CACHE FORMULA:
  per_token_bytes = 2 × num_KV_heads × head_dim × num_layers × dtype_bytes
  total_bytes     = per_token_bytes × sequence_length × batch_size

LEVERS (in order of preference):
  1. num_KV_heads  → reduce via MQA/GQA architecture (must be trained in)
  2. dtype_bytes   → reduce via quantization (last resort)
  NOT changeable:  num_layers, head_dim (fixed by architecture)

MQA DIMENSION RULE:
  Q:  unchanged, full per-head dimension (e.g. 8 × 64 = 512)
  K/V: ONE shared projection across all heads (e.g. 64, not 8 × 64)
  → "Change the projection, not the head."

MQA TRADE-OFF:
  Smaller KV cache  ⇄  Lower "attention diversity"
  (NOT the same thing as hallucination)

CACHING TERMINOLOGY:
  KV cache        → per-request, in VRAM, core inference mechanism
  Prompt cache    → provider-level, short-lived (minutes)
  Prefix cache    → shared-prefix caching across requests, tied to prefill
  App-level cache → ordinary Redis-style caching, not AI-specific

PRODUCTION RULE OF THUMB:
  Model weights ≈ 20-40% of VRAM → reserve 50-70% of remainder for KV cache
  (e.g. H100 80GB, model=20GB → allocate ~50GB for KV cache)
```

### 🟢 Beginner

**Q1.**

**Question:** Why does naive autoregressive decoding recompute K and V at every step?

**Answer:** Because without a cache, the model has no memory of previously-computed K/V tensors, so it recalculates them from scratch for every prior token at every single decode step, even though those earlier tokens never change.

**Explanation:** Directly, explicitly confirmed and walked through with a toy example.

**Why Interviewers Ask This:** Tests whether you understand the actual problem KV cache solves, not just that it exists.

**Possible Follow-up:** "What's the total compute cost across a full N-token generation without caching?"

**Q2.**

**Question:** What do TTFT and TPOT stand for, and which inference phase does each correspond to?

**Answer:** TTFT = Time To First Token, tied to the prefill phase. TPOT = Time Per Output Token, tied to the decode phase.

**Explanation:** Directly, explicitly confirmed.

**Why Interviewers Ask This:** Baseline vocabulary check for inference performance discussions.

**Possible Follow-up:** "Which one dominates cost for a long-prompt, short-output summarization task?"

**Q3.**

**Question:** Is the prefill phase parallel or sequential? What about decode?

**Answer:** Prefill is parallel — the entire prompt's K/V can be computed at once. Decode is strictly sequential — one token at a time, due to the autoregressive property.

**Explanation:** Directly, explicitly confirmed.

**Why Interviewers Ask This:** Tests understanding of why these two phases have fundamentally different performance characteristics.

**Possible Follow-up:** "Why can't decode be parallelized the same way prefill can?"

**Q4.**

**Question:** What is the memory wall?

**Answer:** The mismatch between how fast a GPU can compute (TFLOPS) and how fast data can be delivered to it (memory bandwidth in GB/sec) — compute capacity routinely outstrips the rate at which data can be supplied.

**Explanation:** Directly, explicitly confirmed, with the kitchen/chef analogy.

**Why Interviewers Ask This:** Tests whether you understand that inference bottlenecks are often about data movement, not raw compute power.

**Possible Follow-up:** "How does reducing KV cache size help relieve the memory wall?"

**Answer:** How much computation is performed for every byte of data moved from memory — a measure of how efficiently you're using data once you've paid the bandwidth cost to move it.

**Explanation:** Directly, explicitly confirmed with worked numeric examples.

**Why Interviewers Ask This:** Tests understanding of the metric that actually quantifies the memory wall problem.

**Possible Follow-up:** "Is higher or lower arithmetic intensity always better, and why?"

### 🔴 Advanced

**Q16.**

**Question:** A student proposed storing KV cache entries in system RAM instead of VRAM to free up GPU memory for more concurrent users. Evaluate this proposal.

**Answer:** This defeats the purpose of KV caching. The entire point of the cache is to avoid recomputing K/V — but K/V must be immediately available to the GPU's compute units during the decode phase, which happens in VRAM. Moving the cache to system RAM reintroduces exactly the kind of RAM↔VRAM data-movement bottleneck (the memory wall) that the cache is designed to avoid being subject to in the first place, and the latency of transferring data back and forth for every decode step would likely exceed the cost of simply recomputing K/V. The instructor rejected this proposal directly for this reason.

**Explanation:** Tests whether you can reason about *why* the rejection is correct, not just recall that it was rejected.

**Why Interviewers Ask This:** Senior-level question — tests whether you understand the memory wall deeply enough to catch a plausible-sounding but flawed optimization proposal.

**Possible Follow-up:** "Is there any scenario where offloading part of the KV cache to CPU memory makes sense, even with the latency cost?"

**Q17.**

**Question:** Design a VRAM allocation strategy for a production LLM-serving deployment on an H100 80GB GPU, given a 20GB model and highly variable per-request prompt lengths (some under 200 tokens, occasional spikes to 10,000+ tokens).

**Answer:** Following the rule of thumb from class: allocate the model's ~20GB, then reserve roughly 50GB (60-70% of the remainder) for the KV cache pool, leaving a small safety margin. Because prompt length varies dramatically, the KV cache allocator needs a dynamic eviction policy rather than a fixed per-request budget: evict/free cache aggressively for typical short-prompt requests (clearing after each request or a modest batch of them), while watching for the long-tail spike requests that could consume disproportionate cache space on their own — potentially capping or specially routing unusually long prompts rather than letting a single request starve the pool for everyone else. A fixed TTL isn't necessarily appropriate here since the right eviction trigger is VRAM pressure and request volume, not elapsed time.

**Explanation:** Tests whether you can translate the class's qualitative heuristics into an actual operational policy.

**Why Interviewers Ask This:** Senior-level systems-design question — correctness depends on reasoning about variability and tail behavior, not just restating the static rule of thumb.

**Possible Follow-up:** "How would Paged Attention specifically help with this kind of variable-length workload?" (Note: this ties to content explicitly deferred in this class — a good candidate signal is recognizing that and reasoning from first principles anyway.)

**Q18.**

**Question:** The MQA paper reports BLEU scores nearly identical between MHA and MQA, with a slight edge to MQA under beam search in one configuration. Construct an argument for why a team might still choose MHA over MQA despite MQA's inference-efficiency advantage.

**Answer:** If the deployment is latency-insensitive and VRAM-abundant (e.g., a low-traffic internal tool, or batch offline processing with no concurrent-user memory pressure), the inference-efficiency gain MQA offers may simply not matter, while the "attention diversity" MHA preserves could provide a meaningful edge on tasks requiring nuanced, varied relational reasoning across input tokens — especially tasks sensitive to subtle quality differences that BLEU alone might not fully capture (BLEU is itself an imperfect proxy for many kinds of generation quality). **Explanation:** Tests the ability to argue against the "obviously more efficient" choice by identifying when the efficiency gain's value is context-dependent, not universal.

## 🧪 Scenario-Based Interview Questions

> **Scenario 1:** Your production LLM API is suddenly experiencing high TTFT complaints from users, but TPOT (measured per-token during generation) looks completely normal in your monitoring dashboards.

**Structured Answer:**
1. **Initial investigation:** Check recent changes in typical prompt length — TTFT is tied to the prefill phase, so a shift toward longer prompts (more tokens to process in parallel before the first token emerges) is the most likely cause if TPOT is unaffected.
2. **Metrics/logs to check:** Prompt token-count distribution over time; GPU utilization during the prefill window specifically (separate from decode-window utilization); batch sizes during prefill.
3. **Possible causes:** A new feature sending longer context/prompts (e.g., added RAG context, longer system prompts, document uploads); a change in batching strategy delaying when prefill starts processing new requests; GPU contention specifically during prefill-heavy periods.
4. **Debugging approach:** Correlate TTFT spikes with prompt-length percentiles and with deployment/feature-rollout timestamps; isolate whether the issue is prefill compute time itself or queueing delay before prefill even starts.
5. **Resolution:** If it's genuinely longer prompts, consider prefix/prompt caching for repeated context segments, or trimming unnecessary context; if it's queueing delay, address request scheduling/batching, not the model itself.
6. **Prevention:** Track TTFT and TPOT as separate SLOs with separate alerting thresholds, since they're driven by different phases and different root causes.

> **Scenario 2:** Your team is evaluating whether to retrain your production model from MHA to MQA to cut inference costs, but a stakeholder is worried about a quality regression they heard MQA causes.

**Structured Answer:**
1. **Initial investigation:** Clarify what "quality regression" specifically means for your use case, and check whether your task is sensitive to the kind of "attention diversity" loss MQA introduces, versus being well-served by nearly-identical BLEU-style benchmark performance.
2. **Metrics/logs to check:** Your own task-specific quality metrics (not just BLEU, which the original paper itself shows only a ~0.2-point difference on) — ideally A/B tested on real traffic samples, not just benchmark datasets.
3. **Possible causes of the stakeholder's concern:** Likely based on general awareness that "fewer KV heads = less expressive attention," without the specific numbers — the actual empirical quality gap reported in the literature is small (~1-2%).
4. **Debugging/evaluation approach:** Run a controlled comparison: same training data and hyperparameters, MHA vs MQA architecture, evaluated on your actual downstream task and metrics, not just academic benchmarks.
5. **Resolution:** If quality holds up acceptably on your real task, MQA's inference savings in the KV cache (dramatically smaller cache) are hard to argue against for memory-constrained production serving; if quality drops unacceptably on your specific task, consider GQA as a middle-ground compromise instead (deferred in this course to the next class) rather than jumping straight to full MQA.
6. **Prevention:** Build this kind of architecture-variant evaluation into your model-selection process before committing to a training run, since converting an already-trained MHA model to MQA post-hoc isn't possible.

## 📌 Final Revision Sheet

### ⭐ Core Concepts
- Naive decoding recomputes K/V at every step — quadratic total compute cost without a cache.
- KV cache stores K/V once computed, converting that quadratic compute cost into a linear memory cost.
- Prefill (parallel, whole-prompt) drives TTFT; decode (sequential, one token at a time) drives TPOT.
- The memory wall: compute throughput vastly exceeds memory bandwidth; arithmetic intensity measures how well you use data once moved.
- MQA: same number of heads, one shared K/V projection across all of them; Q untouched.

### ⭐ Important Definitions
- TTFT, TPOT, arithmetic intensity, attention diversity, prompt cache vs prefix cache vs KV cache.

### ⭐ Important Commands/Code
- `use_cache=True/False` in Hugging Face `model.generate()`.
- `torch.cuda.synchronize()` around timing measurements for accurate GPU benchmarking.
- KV cache formula: `2 × num_KV_heads × head_dim × num_layers × dtype_bytes × sequence_length × batch_size`.

### ⭐ Architecture/Process
- VRAM allocation order: model weights first (~40%+), then KV cache, then ~5% headroom.
- Production rule of thumb: model ~20-30% of VRAM → reserve 60-70% of the rest for KV cache.
- MQA must be trained in from the start — not retrofittable onto an already-trained MHA model.

### ⭐ Best Practices
- Prefer FP16 over FP32 for inference-time KV cache (half the memory).
- Treat quantization as a last-resort lever, not a first step, for shrinking KV cache.
- Use `num_KV_heads` reduction (MQA/GQA) as the primary architectural lever for cache size.

### ⭐ Common Mistakes
- Confusing MQA's quality trade-off ("attention diversity" loss) with "hallucination" — they are not the same thing.
- Assuming MQA reduces the number of attention heads — it doesn't; it reduces the K/V projection dimension only.
- Assuming KV cache memory grows quadratically like the uncached compute cost does — it actually grows linearly.
- Storing KV cache in system RAM instead of VRAM — defeats the purpose and reintroduces the memory wall.

### ⭐ Interview Points
- Be ready to state the KV cache formula from memory and identify which factors are actual optimization levers.
- Know the TTFT/prefill vs TPOT/decode split cold — a very common follow-up chain in interviews.
- Be ready to explain why MQA's efficiency gain doesn't come with a meaningful quality gain (and vice versa — why that's still worth it).

- GQA, DeepSeek's MLA, RoPE, Flash Attention, static/dynamic HBM, and Paged Attention are all explicitly deferred to upcoming classes in this series — track them as "owed" content.
